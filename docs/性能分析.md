# 从轨迹发现问题，再验证优化

以下区分三种证据：2026-11-04真实30B历史轨迹、2026-11-06当前采集工具的小模型多卡验证、2026-11-06同入口SiLU算子对照。它们不是同一版本、同一负载，不能拼成一个“整模提升倍数”。原始数据入口见 [outputs索引](../outputs/README.md)。

## 1. 先修正测量，否则会优化错方向

旧SiLU基准预先对PyTorch输入做chunk，却让Triton走完整wrapper，两边入口不一致。本次改成双方都调用 `silu_and_mul(x, backend=...)`，计入形状检查、view/chunk、分配及调用开销。固定seed731，先warmup，再用CUDA event重复计时；**计时结束后另采profile**。

归层分析原先只关联CUDA Runtime API，漏掉Triton的Driver API `cuLaunchKernelEx`。现在Runtime/Driver均使用correlation关联GPU kernel；异步kernel执行晚于CPU范围也能归层，不按时间邻近猜测。对应回归在 `test_profile_tools.py`。

旧工具用lanes做PP并发对照，但当前Core并发由持久batch queue决定。本次移除旧lanes矩阵，改用显式 `max_concurrent_batches`，每个配置独立重启。旧lanes结果不能代表新队列收益。

## 2. 从真实30B trace看到了什么

打开 `outputs/profiles/qwen_ep8_legacy/trace.json.gz`，先只看rank0。其GPU观测跨度约1594.22ms；非NCCL kernel并集约136.84ms，NCCL并集约278.78ms。CPU侧CUDA API累计：`cudaLaunchKernel`约169.17ms，`cudaMemcpyAsync`约165.53ms，`cudaStreamSynchronize`约44.14ms。

这些数字不能相加成总耗时：CPU与GPU异步并行；API包含主机开销/阻塞；NCCL包含等待peer，不能由时长推传输带宽。trace最后一条消息部分尾层缺失，因此只在**完整消息**内比较层耗时，不把全窗口比例当稳态占比。

例如该历史rank0的前两次完整decode消息中，attention归属kernel并集约23ms/次，MoE约73–78ms/次；MoE包含路由、专家和NCCL。prefill与decode应分别比较。细化的非NCCL/NCCL分项及Driver归属修正后的精确数值以 `analysis/summary.json` 为准，不能把MoE总时间都称为GEMM。

在该trace里可以追到大量小专家GEMM、索引/拷贝与host launch。更具体的证据是：当时运行队列已选择 `torch_grouped`，但rank0的312次 `aten::_grouped_mm` **内部嵌套4,992次 `aten::mm`、4,992次 `aten::item` 和 `_local_scalar_dense`**。PP2×EP4的rank0则是334次grouped API内部嵌套10,688次mm/标量读取。分别相当于每次API仍逐16/32个本地专家执行。不要把item与其内部local_scalar重复计为两次独立同步。

这些计数来自同CPU线程、grouped API范围内的子操作，不是把全模型所有mm笼统归给专家；`summary.json` 的 `grouped_api_audit` 可复核。它证明该环境中API并未变成一次融合device grouped GEMM，仍有逐专家控制成本；**尚不能据此断言它解释了全部端到端差距，或把每次item都认定为等时长关键路径阻塞。**

当前 `GroupedExperts` 的loop分支另有 `offsets.tolist()`：一次把偏移交给CPU后循环专家；native grouped分支把device offsets传给PyTorch，但实际底层可能仍分解。因此“把loop换成grouped API”不是一个自动成立的新优化。下一步应验证真正保留device offsets的SM80 grouped kernel、路由/激活融合，并对比易读loop；默认已保留参考loop，不自动强推未经测量的grouped后端。

若继续写kernel：按expert和输出tile划CTA，直接读device offsets，跳过空expert；gate/up合并计算，tile内融合SiLU再接down投影，避免按route复制整份权重。decode的小M与prefill的大M分别选择GEMV/小tile和Tensor Core GEMM策略，并保留top-k回收、权重乘法和FP32归约的数值契约。具体tile、寄存器/共享内存成本需用真实M分布和硬件计数器调整，不能仅凭trace先定一个“最优tile”。

### 计算与通信重叠的实测结论

三组历史八卡trace中，检测到的**同卡非NCCL/NCCL kernel交集为0**。不能把独立stream或非阻塞send当作已经掩盖通信。

PP2的两个stage却有跨卡计算交集：普通组约88.39ms，专用P2P组约95.68ms；分母是两stage所有已观测非NCCL区间并集，对应约9.71%/10.54%。这只是该窗口的跨stage并发，受采样边界、缺尾和profile扰动影响，既不是同卡通信overlap，也不是zero-bubble率，更不是可宣称的吞吐提升。

## 3. 已验证的一个局部优化：按运行模式选择SiLU后端

算子输入 `[T,2I]`，计算 `silu(gate)×up`，本次 `I=768`、BF16、A800-SXM4-80GB、PyTorch 2.9.1+cu130。T是**一次激活调用的行数**，不是用户并发数或上下文长度。每个专家的T通常远小于整个batch token数。

无profiler计时的30轮中位数，单位μs：

| T | PyTorch eager | Triton eager | PyTorch Graph | Triton Graph |
|---:|---:|---:|---:|---:|
|1|21.78|37.82|4.96|2.05|
|128|30.15|42.34|7.91|2.75|
|4096|39.03|42.69|30.37|7.12|
|6144|50.46|42.97|48.42|10.87|
|8192|66.78|42.54|64.22|25.38|

数据和全部计时样本在 [kernel_matched.json](../outputs/kernels/silu_matched/kernel_matched.json)，独立轨迹解析在 [trace_analysis.json](../outputs/kernels/silu_matched/trace_analysis.json)。本组固定随机输入的max_abs_error为0；不代表所有输入/shape或整模型都位级一致。

### trace怎样支持这个解释

打开 `kernel_matched.tokens1.trace.json.gz`，找 `silu.tokens1.torch.eager` 与 `.triton.eager`。每个范围都执行8次完整helper：

* PyTorch：16个GPU kernel，即每次 `silu` 加逐元素 `mul` 两个kernel；总GPU kernel并集42.91μs。
* Triton：8个 `_silu_mul_kernel`，每次一个融合kernel；总GPU kernel并集16.67μs，经 `cuLaunchKernelEx` 提交。
* Graph范围：每次replay含16对PyTorch/Triton调用，共8次replay，因此384个kernel是预期值，并非多算了一个模型batch。

小shape上，**Triton设备执行更短，但eager事件跨度更长**：CUDA event记录的是重复调用整个序列的GPU时间跨度，主机提交慢导致的GPU空档也在其中。Triton Python wrapper/launcher开销、分配/调度等固定成本压过这几微秒设备收益；不是“PyTorch做了更少数学”。profile的CPU范围还受profiler首次记录等额外开销影响，所以不能拿带profile的CPU总时长替代无profile计时。

Graph把已捕获调用重放，显著减少Python与逐次launch间隙，设备侧融合收益更容易体现。大shape下，中间张量读写与设备计算成本增加，融合更划算，6144/8192行的eager也测到收益。Graph收益不只来自kernel数量，还包含中间读写减少；不能仅凭kernel计数断言带宽或occupancy原因。

同一T的Graph显存地址复用、热缓存和紧邻重放与真实专家调度不同。这里没有硬件带宽/occupancy计数，T8192时Graph Triton耗时上升的细因尚未确定，不能凭拐点虚构寄存器或带宽瓶颈。

### 已落地的选择规则与边界

`silu_and_mul`默认auto：只有已测的 **A800、BF16、连续输入、I=768且T≥6144** 才自动选Triton；其它情况保留PyTorch。显式 `VLLM_LEARN_SILU_BACKEND=torch|triton` 可做对照，Triton不支持的布局/dtype会明确报错。设备判定缓存，避免每次查GPU名称。

相对无条件选Triton，小输入T1保留PyTorch约21.78μs，对照Triton37.82μs；T8192选择Triton约42.54μs，对照PyTorch66.78μs。都是**单算子**，不能换算成已验证的整模型tok/s。当前engine强制eager，没有整模型CUDA Graph；不能直接把Graph单算子2.4–4.5倍写入简历的端到端收益。

复现：

```bash
CUDA_VISIBLE_DEVICES=0 python v9/tools/kernel_bench.py \
  --tokens 1 128 4096 6144 8192 --intermediate 768 --dtype bf16 \
  --warmup 30 --iterations 100 --repeats 30 --profile \
  --output outputs/silu_recheck/result.json
```

`result.tokensN.trace.json` 中，`torch.eager` / `triton.eager` 是各8次调用；`both.graph` 是16对操作的graph重放8次。计时JSON先于另一次采样过程产生，避免把profiler开销掺入表格。

## 4. 不同负载怎样选并行，怎样形成真正的优化证据

1. **定义目标**：固定卡数、显存和质量门槛。离线优化output tok/s；在线先限定TTFT/TPOT或P95/P99，再找满足SLO的最大吞吐。不要只比峰值tok/s。
2. **冻结条件**：同一token IDs、到达模式、输出长度、模型/源码SHA、dtype、Attention/专家后端、KV预算。预热后交替A/B多次运行，保存逐请求数据和失败。
3. **找关键路径**：按prefill/decode分别看逐层Attention/MoE的compute/NCCL并集、CPU launch/同步、专家M分布、跨stage等待。先检查漏事件与采样边界。
4. **只改一个因素**：TP8↔TP4PP2改变拓扑；单一拓扑下改在途深度；或只改专家后端。一次改变三个因素就无法归因。
5. **预测trace变化**：grouped GEMM应减少逐专家launch/同步；队列填充应增加稳态跨stage计算交集；真正通信overlap应在同卡不同stream出现C∩N；融合应减少中间kernel。
6. **验收**：固定前缀logits和cached输出通过，再用无profile运行报告tok/s与长尾；trace另采并验证预测。若整模无收益，记录局部收益被其它瓶颈覆盖，不挑好看的截图。

短decode、低并发时专家M很小，launch/GEMV和通信等待可能主导；深PP可能增加fill/drain成本。并发提高后，小GEMM可能变成有效GEMM，但不同专家负载偏斜仍需看分布。长prefill通常更多矩阵计算，长context decode则更多读KV；两者不能只按“长度长”归为一个场景。

EP减少每卡专家权重，却增加dispatch/combine；TP使Attention/FFN矩阵分片并引入collective；PP减少层权重与部分组规模，却增加stage依赖和activation传输；DP提高请求并行度，但EP跨DP后空闲副本仍参与collective。最优方案依赖请求独立性、实际M、KV/权重带宽、拓扑和SLO，不能预先宣称PP×EP总是最优。

历史同机无profile对照保留在 `outputs/benchmarks/legacy_20261104`，例如short128当时自研约113tok/s、vLLM TP8约1375tok/s。它们是旧版、限定负载与质量边界的结果，不是本轮清理后新版本的性能，也没有形成新的整模前后收益。**本轮完成了可复核的采集/分析链和一个算子级后端选择优化，未新增30B端到端加速认证。**
