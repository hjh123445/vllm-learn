# 架构与阅读顺序

只读当前 `v9`。建议按这条链路理解一次请求，而不是按文件名逐个背：

```text
example.py / server.py
  → AsyncEngine（在线）或DPFrontend（多个副本）
  → EngineCore：唯一调度者，维护持久batch_queue
  → Scheduler：token预算、chunked prefill、请求/KV所有权
  → MultiprocessExecutor：每worker FIFO提交、Future、独立结果回收
  → worker_main：绑定设备、建立通信组、处理消息
  → ModelRunner：构造输入、PP收发、执行模型、末stage采样
  → Qwen3MoeModel：embedding、本地decoder层、末stage norm/head
  → layers：Attention、MoE、TP linear、Triton算子
```

## 核心文件

| 文件 | 先看什么 |
|---|---|
| `v9/engine/core.py` | `_PendingBatch`、提交/按序回收；schedule输入是快照 |
| `v9/engine/scheduler.py` | `in_flight`、num_cached与num_scheduled、取消与抢占 |
| `v9/engine/executor.py` | SHM消息与ACK；独立线程消除全rank控制ACK屏障 |
| `v9/engine/worker.py` | 设备/进程组初始化；调用runner；唯一输出rank |
| `v9/engine/model_runner.py` | prefill/decode输入、PP边界、KV、末stage输出 |
| `v9/models/qwen3_moe.py` | 本地层区间；模型本身不收发activation、不采profile |
| `v9/engine/pipeline_transport.py` | NCCL P2P、stream/event、发送buffer存活、receive |
| `v9/engine/frontend.py` | 每DP独立EngineCore进程及卡集合；EP空副本参与 |
| `v9/engine/process_groups.py`、`v9/layers/parallel.py` | 坐标到通信组、TP linear与collective |
| `v9/layers/moe.py` | router、token ownership、变长dispatch/expert/combine |
| `v9/layers/kernels.py` | RMS/QK参考路径与实验融合算子、SiLU后端选择 |
| `v9/utils/observed_runner.py` | 显式实验适配器；普通engine不依赖它 |

`tests`用于自动验证契约，不是运行引擎必须经过的链路。`tools`是离线实验入口，不应由模型反向导入。已删除历史bench/probe脚本与重复报告，保留保护调度、并行和数值的回归测试。

## 当前PP是什么

采用V1风格普通batch queue：一个EngineCore维护多个在途batch，默认上限PP size，结果按序回收，再安排依赖该结果的下一chunk/token。每个物理rank负责一个连续层区间。例：48层、PP2时，每个TP rank在stage0持前24层，stage1持后24层。

每个请求最多一个在途batch；长prompt可拆chunk，但同请求的后续chunk仍保守等待前一结果回收。多个独立请求才可充分填满流水线。一条短decode请求不会因为队列槽位多就变出独立工作。

stage边界传 `IntermediateTensors`：`hidden=[T,H]` 与可能的 `residual=[T,H]`。延迟残差相加的实现不能只传hidden。首stage做embedding，末stage做最终norm/head/sample；中间stage仅算自己的层。

这里的首/末stage描述执行位置。目前每个stage仍构造embedding、最终norm与lm_head，只有decoder层真正按stage裁剪；warmup和诊断工具还依赖这些模块的属性。进一步减少这部分复制需要一起调整这些消费者，不能把它们当作无引用字段直接删除。

`pipeline_lanes`、transport lane及未接入执行器的虚拟stage规划器已删除。PP并发只由 `EngineCore.batch_queue` 和 `max_concurrent_batches` 控制，默认上限为PP size；使用 `--max-concurrent-batches` 做对照。当前没有interleaved virtual-stage调度、训练1F1B/DualPipe或zero-bubble保证。

PP send使用独立stream/event并保留activation引用；receive按共同调度消息中的token数与runner dtype分配 `[T,H]`，仅收hidden/residual，不再发送或回读GPU形状header。各stage必须消费相同FIFO调度序列；没有跨端header校验来兜底形状/批次错位。异步receive仍需等待通信完成建立计算依赖，不是预投递接收调度器。专用P2P communicator减少collective顺序耦合，但不自动证明实际重叠。必须结合CUDA trace和不带profiler的性能对照。

## EP为什么是DP×TP

无CP时设备数 `DP×PP×TP`，开启EP后：

```text
ep_size = dp_size × tp_size
ep_rank = dp_rank × tp_size + tp_rank
global_rank = (dp_rank × pp_size + pp_rank) × tp_size + tp_rank
```

每个固定PP stage有一个跨DP×TP的专家组。Attention在本DP的TP组切头；专家按完整expert分片到EP组。每rank只存本地专家 `w13=[E_local,2I,H]`、`w2=[E_local,H,I]`。

1. 本DP复制的Attention输出为 `[T_d,H]`，router先保持完整M形状计算。
2. 再在TP ranks之间划token ownership，避免同一token重复dispatch。
3. 按目标owner排序，交换真实counts；变长all-to-all发送activation与metadata。
4. owner按本地专家计算，再reverse all-to-all，恢复源token与route顺序。
5. 合并top-k权重，只在原DP的TP组gather，恢复本DP `[T_d,H]`。

dispatch/combine不做固定专家容量padding；TP输出gather的等长接口在ownership边界可能填最多TP−1行。EP已持完整专家，不应再把结果当作专家TP部分和做额外all-reduce，也不能跨整个EP组gather混入别的DP请求。

DP空闲rank仍持其他DP可能调用的专家，必须按相同collective顺序参加空批处理。当前离线DPFrontend每轮仍等待副本，存在慢副本屏障。推理DP没有训练梯度/优化器，不称为训练DDP/ZeRO-1。

## 数据经过哪里

SHM是CPU控制消息/输出token的IPC，不是GPU activation的TP通信后端。TP/EP/PP的CUDA张量通信使用NCCL；底层是否走NVLink、PCIe、IB由拓扑与NCCL选择。kernel名是NCCL不等于已经证明走NVLink/IB；用 `nvidia-smi topo -m` 和NCCL debug日志确认。单机八卡实验不能据此宣称验证了跨机IB。

### `.cpu().tolist()` 可以删到什么程度

CUDA张量的 `.tolist()` 已经隐含搬到CPU；仅删除 `.cpu()` 不会消除同步。GPU里的数据不能直接变成Python `list[int]`。应先判断消费者在哪里，再决定能否移除整次回读：

| 位置 | 当前做法与原因 |
|---|---|
| PP activation形状 | 已删除GPU header回读。`T=input_ids.numel()` 是CPU可读的张量元数据，`H/dtype` 来自配置，不读activation值 |
| EP变长通信 `send_counts/recv_counts.tolist()` | 保留。PyTorch `all_to_all_single` 的 `input_split_sizes/output_split_sizes` 接收主机整数列表；activation、expert ID与结果仍通过CUDA/NCCL传输。GPU cumsum可描述分段，但不能直接作为此API的split参数 |
| 专家reference loop的 `offsets.tolist()` | 保留。Python循环要用专家边界切片；`torch_grouped` 分支把offsets留在GPU，但支持性、性能与数值应单独验证，不能为删一行强制替换后端 |
| 末stage采样 `.tolist()` | 保留。当前CPU调度器要判断EOS、追加token并经IPC返回结果；完全驻GPU需要异步输出与调度重构 |
| SDPA/DCP参考路径 | 仍有序列长度和索引回读，是明确的参考实现成本；不宣称整个引擎无CPU同步 |
| 数值诊断/trace导出 | CPU落盘是工具目的，独立于普通模型路径 |

### 参数只有一个来源

worker只接收一个 `ParallelTopology`，从它派生DP/PP/TP/CP坐标。独立 `ep_size/ep_rank` 参数已删除；`STATE.ep_size/ep_rank` 是仍被专家分片和通信读取的只读派生属性，不能当作废字段删除。

模型移除未使用的layer编号与尺寸缓存；层号由 `ModuleList` 的全局索引保留，外置profile仍能定位每一层。`Config.tensor_parallel_size` 的重复副本和无执行分支的 `enforce_eager` 开关已删除；TP使用 `EngineCore(tp_size=...)`，或在线入口的 `tensor_parallel_size` 别名。整引擎目前执行eager；算子微基准的CUDA Graph不代表整模Graph模式。

当前文本入口没有媒体processor/encoder、embedding拼接、MRoPE或Talker。模型名称包含Omni不代表整个多模态服务链已经实现；HF多模态功能probe也不能替代自研路径验证。
