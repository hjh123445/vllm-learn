## 20:40 最新复核：新增逐请求模式复现跨 batch 数值差异

本节优先于下方较早的“数值分歧尚未定位”描述。使用 172.28.30.56 上同一模型权重、同一个合成 token 输入，分别以单请求和重复请求组成 batch 执行；只比较 batch 的第一个请求。将诊断器改为 forward-pre-hook 后，输入快照在模块运行前复制，避免 residual 原地更新污染输入记录。新测试 `test_activation_capture.py` 已在该机通过。

| 场景 | 首个可见差异 | 受控重放 | 解释边界 |
|---|---|---|---|
| 1024-token prefill，batch=1 vs 3 | 第 0 层 `o_proj`，670,271/2,097,152 BF16 元素不同，max abs 0.00390625，RMSE 3.78e-5 | 相同输入和权重的 BF16 `F.linear` 重放逐元素复现；FP32 输入/权重乘法、再转 BF16 后，两个 M 形状结果 exact | 支持 prefill `o_proj` GEMM 形状相关舍入为该处差异来源；不证明每个层/其他长度也能由 FP32 累加消除 |
| 47-token prompt，batch=1 vs 8 | 第 0 层 `q_proj`，101/192,512 元素不同，max abs 1.2207e-4，RMSE 1.023e-6 | 相同矩阵重放复现；把同一线性按每请求 M=47 分段后，八份重复请求输出 exact | 同时测得全 batch 单 GEMM 0.0426ms、逐请求分段 0.1618ms，约 3.8× 慢；这是单个投影微基准，不是端到端退化比 |

短输入 q_proj 的 FP32 累加重放仍有 50 个元素不同（max abs 4.8828e-4），所以“全部换 FP32 累加”也不是已经验证的通用修复。MoE router、按专家分组的 GEMM、归一化、cache 更新及各自执行形状还会影响后续结果。为了严格跨 batch 复现，可能需要统一/固定每算子形状或使用分段执行，但吞吐、内存和全模型语义尚未验证；当前不把局部 workaround 加成默认路径。

这不是 EP token 丢失证据：首个差异出现在 replicated 输入上的 dense attention projection；相同路由与变长 all-to-allv 组件仍由独立分布式 oracle 验证。之前 EP8 与 PP2×EP4 的匹配路径 384/384 logits exact 只覆盖列出的 12 条合成样本、指定 backend 和固定前缀，不等于全负载或跨 batch 的严格一致。

### 20:40 逐请求诊断和 PP2×EP4 集成复核

代码把原先仅用于诊断的 `VLLM_LEARN_SERIALIZE_REQUESTS` 收敛为显式 `batch_execution_mode=per_request`，默认仍是 `batched`。在 EP8 的 47-token batch=8 和 1024-token batch=3 中，per_request 均使捕获的 L0/L1/L2/L47 边界、router、MoE、lm_head 与单请求逐元素相同；1024-token 默认 batched 仍在 L0 `o_proj` 出现 670,271 个差异元素并改变第二 token。PP2×EP4 的 47-token batch=3 per_request 也捕获了 stage0 L0 与 stage1 L24/L47 的 Attention/MoE/block 及 lm_head，输出逐元素相同，远端 CPU 4项回归通过。

这不是把串行化当作性能优化：它固定了 M 形状，代价是失去 GEMM 融合。它可作为回归/保守质量路径，不能据三个受控样本宣称跨所有 batch、长度和 kernel 的严格确定性。相应原始 metadata、逐文件 SHA 清单和选定张量保存在 `batch_shape_probe_056_20261104_194535`、`batch_shape_probe_056_20261104_201451`、`batch_shape_probe_056_20261104_201826`、`batch_shape_probe_056_20261104_203819`；后两个大包的完整张量仍保留在远端，不把未下载部分写成已核验本地证据。

PP2×EP4 这次部署快照中的 74 个 Python 源文件均与本地工作树 SHA256 一致；Markdown 文件在实验后更新，不纳入运行代码一致性结论。详见 `batch_shape_probe_056_20261104_203819/deployment_verification.json`。

本次取证还修正了诊断工具：旧 hook 在 forward 后才复制 module 输入，decoder block 的 residual 参数已被原地改写；现在由 pre-hook 在调用前复制，并新增单元测试。完整原始张量与逐文件校验清单放在 `batch_shape_probe_056_20261104_183715/` 和 `batch_shape_probe_056_20261104_185532/`；第二次逐层取证放在 `batch_shape_probe_056_20261104_185532/activation_comparison.json`。这些是数值诊断数据，不是性能 trace。

## Attention 后端与 prefill 切分消融

原始目录：[Attention 消融](ablation_056_20261104_105934/)。以下实验使用 reference math、模型 dtype router logits、ownership、source weight 和 PyTorch grouped 专家路径。

独立显式 attention oracle 检查 chunk prefill、decode、GQA、乱序物理 pages，两种 GQA 策略均通过语义测试。在真实 Qwen attention 尺寸的随机 BF16 输入上，profiler 观察到：

| Q/K 长度 | 显式重复 KV / 默认策略 | masked GQA | 两策略最大绝对误差 |
|---|---|---|---:|
| 128/128 | Flash Attention | Flash Attention | 0 |
| 512/1024 | efficient attention | math attention | 0.001953125 |
| 4/4100 | efficient attention | math attention | 0.00048828125 |
| 1/4097 | Flash Attention | Flash Attention | 0 |

这说明 API 的 `enable_gqa` 可改变实际 backend。它是组件层证据；不能推出整个模型的误差已经解释完。默认诊断策略改成与 HF CUDA 的 masked KV repeat 一致，保留旧策略开关便于复现。

| 改策略后的配置 | 固定前缀匹配 | 连续生成完全一致 |
|---|---:|---:|
| EP8，budget512，单独 | 46/48 | 9/12 |
| EP8，budget8192，单独 | 44/48 | 7/12 |
| EP8，budget512，批量 | 42/48 | 本轮未测 |
| PP2×EP4，budget512，单独 | 44/48 | 9/12 |
| EP1，budget512 | 两次 teacher 启动 OOM，不能记分 | cached 后续完成 9/12 |
| EP1，budget8192 | 同上 | cached 后续完成 7/12 |

两次 EP1 teacher OOM 时，另一进程占用约 27.24 GiB，权重加载阶段就已放不下；之后该占用变化，cached 单卡任务可运行。不能把这两次失败算成算法不正确，也不能删除失败日志后只展示成功。

扩大 whole-prefill budget **没有统一提高匹配率**。当前不能给出“只改 chunk 或 GQA 就修好了”的结论。

## 接下来怎样区分实现错误与执行形状差异

HF 的原参考来自 cached generate，而 teacher forcing 会重新计算完整前缀。即使 token IDs 相同，KV 的计算历史和 GEMM 的 M 维不同，低精度计算图也不同。因此要先做 HF 自身对照，而不是把 HF cached 与自研 fresh 的所有差异直接叫通信错误。

有限队列已运行 HF 同一 48 个前缀 fresh forward、单卡 budget512/8192，以及失败前缀 `context1k8/index1/prefix3` 的 EP1/EP8 全局 48 层边界捕获。只保存每个边界首尾行用于定位，不把它叫完整激活逐元素认证。

这组队列补充出两条诊断证据：

- HF 的 fresh full-prefix 与早先 cached `generate` 参考自身只有 **45/48** raw-logit top-1 相同，证明执行形状本身足以带来少数离散 token 分歧；因此不能把 custom-vs-HF 的所有差异算作通信错误。对齐 HF fresh 后，EP1 budget512 为 44/48、whole 为 46/48。
- 对固定 `context1k8/index1/prefix3`，EP1 与 EP8 的完整 replicated attention 输入在 L1 attention 完全一致，但 L1 attention 输出已出现 BF16 差异：max abs `0.00048828125`、RMSE `8.07e-6`，之后逐层传播。EP1 和 EP8 最终 token 都为 104183，与该样本 HF continuation 相同。这里是“EP1 对 EP8 首个可见差异”，还不是“HF 对 custom 首个差异”。

HF fresh-reference logits 以及 EP1/EP8 capture 的完整文件已下载并逐文件 SHA 校验。HF capture 单独任务因 JSON 元数据含 Python set 而在安装 hooks 前失败，所以当前还不能列出 HF 对 custom 的首个层级差异。EP1/EP8 的 router hook 在 ownership 下采到不同全局 token 子集，直接按行比较 router 输入/indices 是无效的；分析时只把全局 replicated attention 边界作为可对齐证据。分析 JSON `layer_differences.json` 为空是因为 HF capture 缺失，不应误读成没有分歧；可读的 EP1/EP8 层比较在 `ep1_vs_ep8_layer_differences.json`。

诊断新增 `max_kvcache_blocks`，从自动估算的安全预算再取上限，避免短正确性实验无谓申请大 KV 池；64 blocks 在本模型单卡约 1.61 GB。负预算改为说明 total/used/model/budget 的 RuntimeError。这个上限不会让本来放不下的权重变小。

## 面试时怎样准确描述

“我发现默认复制 attention 输入的 EP 会重复派发 routes，用 ownership 减少了重复工作。随后我没有只报吞吐，而是做空 source/变长/TP×EP oracle，再做 HF 固定前缀与缓存生成验证。扩大样本发现仍有分歧，于是控制 router dtype、GEMM 形状和 masked attention backend，用 HF 自身对照和逐层 capture 区分来源。当前组件通过，全模型尚未完成等价验收；我保留了失败和负收益。”
