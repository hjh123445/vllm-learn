# 准确性修复与在线服务复核

2026-11-04，172.28.30.56，8×A800 80GB。实验继续进行，未完成项目不计为通过。

## 20:40 最新准确性结论：两处实现根因已修，默认 batch 形状差异仍存在

用户问的“准确性问题”是：相同模型权重和 token 前缀，greedy 下一 token/logits 会随 reference 路径、并行形态和 batch 执行形状而变。它不能一概称为 MoE 通信漏数据，也不能仅看 raw token 不同就断言某一拓扑算错。

已通过受控重放定位并修复两处代码问题：

1. **RoPE 预计算设备错误。** 旧路径在 CPU 生成 sin/cos 表再拷至 GPU，与 HF 在目标 GPU 上执行 FP32 频率乘法、三角函数存在舍入差异。改为目标设备 FP32 生成，避开共享模块重复建表。固定 Q/K/V 重放确认旧误差可复现。
2. **EP ownership 改变 router GEMM 的 M 维。** 旧路径先按 token ownership 切输入，再算 BF16 router logits，数值可能改变。现默认对完整复制输入先算 router，再只分发当前 EP rank 拥有的 tokens。分布式变长 all-to-allv oracle 覆盖空 source、非等长 source 与 TP2×EP2，路由计数无缺项。

最新新增的 batch 形状诊断表明，**跨形状数值差异仍未修好**：短 prompt batch=1/8 首差在第 0 层 q_proj；1024-token prefill batch=1/3 首差在第 0 层 o_proj。把捕获到的相同输入和权重在 A800 上重放，BF16 `F.linear` 可复现差异。长 prefill 的 o_proj 用 FP32 乘法后再转 BF16 时两种 M 形状相同；短场景 q_proj 的 FP32 重放仍有 50 个元素不同。因此它是低精度矩阵乘与 batch/M 形状共同作用的证据，不是通用精度修复。为固定每请求 GEMM 形状而逐请求分段，一个 q_proj 微基准约慢 3.8×；不能据局部结果直接改默认服务路径。

activation capture 原先使用 forward hook 复制输入，但 Qwen decoder block 会原地更新 residual，造成部分“输入”快照实际已经被改写。已改成 forward-pre-hook，并在远端通过新增单元测试。先前依赖受污染 block-input 快照的定位结论应以本节表格和 `056正确性与消融复核.md` 的新实验为准。

## 20:40 新增：逐请求模式是诊断/保守选项，不是默认修复

为避免把临时环境变量误当成产品开关，代码新增 `Config.batch_execution_mode`：默认 `batched` 保持融合批处理；`per_request` 在每个 worker 内按请求顺序分别 forward，保持单请求 GEMM 的 M 形状。该模式会牺牲批量融合吞吐，适合数值复现、回归和极端一致性要求，不应直接作为在线默认。

在同一 A800 主机、同一输入和参考路径上复核：

| 拓扑/输入 | 模式 | 首个差异与输出 |
|---|---|---|
| EP8，47-token，batch=8 | per_request | L0 q/k/v/o、router、MoE、lm_head 捕获逐元素相同；两步输出相同 |
| EP8，1024-token，batch=3 | per_request | L0/L1/L2/L47 捕获边界逐元素相同；两步输出相同 |
| EP8，1024-token，batch=3 | batched | 首差 L0 `o_proj`，670,271/2,097,152，max abs 0.00390625；第二个输出 token 从34859变为108704 |
| PP2×EP4，47-token，batch=3 | per_request | stage0 L0、stage1 L24/L47 的 Attention/MoE/block 与 lm_head 捕获逐元素相同；CPU 4项回归通过 |

这证明逐请求模式在三个受控条件下能够消除观测到的 batch 形状分叉，也证明 PP2×EP4 的 stage 消息和结果在该小样本中对齐；它没有证明任意长度、任意并发或默认 batch 路径都严格确定。完整 batch-invariant 修复仍需评估固定 tile/累加精度、性能和显存，不能只把所有请求串行化。

PP2×EP4 这次部署快照中的 74 个 Python 源文件均与本地工作树 SHA256 一致；两个 Markdown 文件因实验后补写报告内容而不同，不影响运行代码一致性。具体核验见 `batch_shape_probe_056_20261104_203819/deployment_verification.json`。

所以准确说法是：RoPE 和 EP router 两处已修；EP/PP 通信缺项在当前 oracle、逐请求 PP2×EP4 和匹配 backend 对照中没有证据；默认 batched 路径的 BF16 GEMM 舍入仍会引发离散 top-k/greedy 分叉，per_request 是已实现的保守诊断选项，全模型 batch-invariant 仍未验收。已有 384/384 结果是限定合成输入、匹配路径和固定前缀的 logits 对照，不是所有 batch 形状上的准确率证明。

结论：先前拿“自研变长批处理”逐点比较“HF单请求路径”造成371/384这一表象；形状匹配后，自研批量对逐请求SDPA参考384/384且logits完全一致，EP与PP×EP也一致。因此在这组输入上没有证据支持MoE all-to-all丢token或EP归约漏项。另一方面，同一引擎单请求与批请求仍有11/384个forced-prefix raw greedy winner变化；这是跨batch形状的数值敏感性，不能仅凭本小样本证明根因全部来自BF16 GEMM或保证任意在线负载输出稳定。

普通HF批量路径和拆分路径也会产生不同 logits，说明不能把HF任意一种批调度的结果当成数学上唯一的逐token基准。报告分别保存单请求HF、批处理HF、拆分SDPA HF三种路径及原始logits，引用准确率时必须注明batch与kernel路径。

后续自然greedy rollout（12条固定合成prompt，输出最多32 token）：EP8和PP2×EP4单请求都与HF逐请求raw greedy的12/12全文完全一致；两种自研拓扑的batch全文一致数均为5/12，首次分歧位置在1到25 token。EP8与PP2×EP4对应的batch输出完全一致。它证明本测试的batch路径可改变输出，并能放大早期winner变化；但匹配batch形状的logits对照完全一致，所以本轮没有发现EP/PP通信造成的缺失结果。已修复的是RoPE设备舍入和EP ownership/router形状实现问题。剩余跨batch shape差异尚未修复，其确切算子成因还没有完全隔离。若要求跨形状严格复现，需固定执行shape/算子，或评估更高精度路径，并以准确率、吞吐和显存共同验收。

## 准确性问题是什么

相同权重、相同 token 前缀、greedy 采样时，自研引擎与 HF 的下一 token 或连续生成不同。它不等同于专家 token 丢失，也不能未经定位就全部归因于 BF16。需要分别检查通信完整性、数学实现和执行形状。

本轮查实并修复两处原因：

1. RoPE 原来在 CPU 预计算 sin/cos 再搬 GPU；HF 在 GPU 上进行 FP32 频率乘法和三角函数。1027-token 样本的 cos 少量 BF16 元素差异最大为 0.0009765625，旋转后 Q 差异最大 0.015625。固定同一 Q/K/V 重放，HF GPU RoPE 下 o_proj 输入误差为零，CPU RoPE 恰好复现原 Attention 误差。修复为在目标设备执行 FP32 运算重建表，避免共享模块重复重建。
2. EP ownership 先切 token 再运行 router，改变 BF16 GEMM 的 M 维。本样本 expert IDs 不变，但路由权重最大差异为 0.0009765625。相同输入和专家权重重放，全量 router 的 MoE 输出误差为零；切片 router 恰好复现 EP8 第一层 MoE 最大误差 0.001953125。改变专家内部 token 排序未复现差异。现默认在完整复制输入上计算 router，再仅派发本 rank 的 token。仍只派发一份专家 route；局部 router 保留为显式实验选项。

## 运行问题修复

- AsyncEngine.generate 原先漏收 token，结束返回空列表；现收集结果并传播异常。
- 提交请求原先与整个GPU step共锁；改为command queue，在step边界由唯一owner修改scheduler。
- 完成、取消、异常清理活跃states/seqs及admission slot，避免扫描历史请求。
- 有界admission及token buffer，慢消费者溢出取消对应请求，不阻塞引擎。
- owner线程执行取消并释放KV；停止/异常唤醒等待客户端，避免并发关闭运行中的core。
- HTTP补充SSE终止、Unicode尾部处理、错误传播、输入/输出/上下文限制、超时和断连取消。
- scheduler抢占原先可能释放已排入本步forward的KV，并从旧running快照再次处理已抢占对象。现排除本步已调度对象，跳过旧快照项，统一维护waiting/running成员关系。

CPU并发回归5项、loopback HTTP协议回归2项、KV抢占回归1项通过。涵盖step阻塞时提交、取消、慢消费者、worker异常、重复完成清理、Unicode及SSE。

client TTFT从HTTP发起到首个非空文本计时，不把role-only块算首token。SSE片段可能合并token，片段间隔不是逐token ITL；另存engine每token发布时间。实际吞吐按output_ids/token数统计。保存parse、template、tokenize、submit、enqueue、publish、flush和结束时间；CPU边界不能替代CUDA时间。

首个EP8/budget512已取得：C1的16请求、C8/C32/C128各512请求全部成功，完成后active=0。TTFT P50依次约161ms、357ms、533ms、1905ms；C128的P99约5136ms。并发增加同时推高尾延迟，尚不能仅据此给出最佳并行配置。后续场景继续运行。

## 面试证据链

动机是研究MoE的数据所有权、低精度计算形状与在线调度，而不止复现并行接口。发现同前缀输出差异后，先排查通信少项，再逐层定位首次偏差，用固定输入重放证明RoPE与router形状的因果关系，修复后回归多拓扑和真实HTTP，同时保留未对齐的cached/批量/融合路径结果。

面对“是否保证完全正确”的追问，应区分指定样本逐层exact、48/48 next-token以及任务准确率三种证据强度。现有结果不能替代完整cached、批量、长输出和任务质量评测，也不证明超过vLLM。
