# 动态负载并行策略与简历证据

本文回答两个面试问题：怎样用可复现证据选择推理并行配置；怎样定位并验证推理数值分歧。材料包含 172.29.226.143 的历史候选吞吐矩阵，以及 172.28.30.56 的后续数值复核、在线实验和 CUDA trace。下文 DP4×EP2 的 304.6/24.6/69.2 tok/s 属于前者，不能与后者的安全参考数学路径拼接为同机优化前后数据。吞吐采样与 profiler 采样分开；所有结论限定在记录的输入、软件、dtype 和执行路径内。

## 可放入简历的两条项目描述

**动态负载并行分析：** 在 8×A800 上构造短输入、4K 上下文、长短混合和分批到达负载，对 EP8、DP×EP、PP×EP 做三轮吞吐扫描，并用 Perfetto 标注 GPU/rank、CUDA stream、全局层、Attention/MoE、microbatch 与 NCCL。测试矩阵中 DP4×EP2 的短128、4K×8、mixed64 输出吞吐分别为 304.6、24.6、69.2 tok/s；EP8 为 112.0、10.8、52.2 tok/s。轨迹用于解释热点和 stage 等待，吞吐由独立无 profiler 运行测量；该排名仅代表记录的 BF16 候选实现，不等于所有拓扑均通过了同一路径的完整质量验收。

**推理数值校验与根因定位：** 建立固定输入的 teacher-forcing、完整 logits 对比、逐层 pre-hook 捕获、EP1 隔离基线、变长 all-to-allv oracle 与算子 replay 流程；定位并修复 RoPE CPU 预计算舍入差异及 EP ownership 改变 router GEMM 形状两处问题。匹配执行路径下，EP8/PP2×EP4 对 12 条合成输入的 384 个固定前缀位置与参考 logits 逐元素相同；另复现默认 batch GEMM 形状引发的剩余分歧，未将局部 workaround 宣称为全模型精度修复。

面试时如果只留一行，可将第一条压缩成：

> 建立 8×A800 动态负载并行评估与 CUDA/NCCL trace 分析链路，覆盖短/长/混合请求及 EP、DP×EP、PP×EP；在记录的 BF16 候选矩阵中 DP4×EP2 于 short128、4K×8、mixed64 达 304.6/24.6/69.2 output tok/s，并通过分层 Perfetto 标注识别 Attention/MoE 热点与流水线等待，明确结果仅适用于该实现和质量验收范围。

如果需要更稳妥、不给候选吞吐过多版面，可不写 tok/s，只写“构建矩阵并给出负载相关排名，保留未通过一致性验收的方案”。

## 一、如何系统选择并行策略

### 1. 先确定优化目标与负载，而不是先选并行名字

先与服务目标对齐：目标是降低 TTFT、TPOT 或 P99，还是提升输出 goodput；同时约束显存、数值质量和并发。把请求分层记录：输入长度、输出长度、并发、到达过程、batch/token budget、前缀复用率、prefill/decode 比例。短请求、高并发；长上下文、小并发；长短混合；突发/泊松到达会产生不同瓶颈，不能用一个平均长度代替。

本次候选矩阵包含 `short64`、`short128`、`context1k8`、`context4k8`、`mixed64`、`arrival64`，每个配置三轮，记录吞吐、TTFT/TPOT 分位数和输入 fixture 指纹。矩阵中的 `arrival64` 是按 engine step 引入请求的可复现场景，不等同于生产墙钟 QPS。正式吞吐在未开 profiler 的独立运行中测量。

### 2. 先验收 trace，再用 trace 提出可证伪假设

阅读 trace 的次序：

1. 确认 CPU API 与 CUDA kernel 都在文件里；逐 rank 检查 GPU 活动、层覆盖、消息/microbatch 覆盖和共同时钟。缺失层/消息的区间不用于算气泡或做拓扑排名。
2. 从请求/批次到 stage、全局层、Attention/MoE、CUDA stream，沿时间线追一条完整消息。CPU 的 `aten`/launch 是提交活动，CUDA kernel 才是设备执行；二者不能混作一个时长。
3. 用同一 GPU/rank 上的 CUDA kernel 区间计算活动区间并集。layer annotation 是父级包络，可能包括 NCCL、kernel 和等待，不能与子 kernel 时间相加。
4. 通信重叠必须比较同一 GPU 上 NCCL kernel 与计算 kernel 的区间交集，并检查 stream、事件依赖和资源竞争。NCCL kernel 的 duration 可能含轮询/等待，并不等于链路纯传输时间。跨 GPU 同时活动是 pipeline 并发，不是单 GPU 通信/计算重叠。
5. 由 trace 提出具体假设，再用单因素消融和无 profiler 吞吐、TTFT/TPOT 复测。profile 变慢不作为性能数字。

### 3. 用相同 fixture 测配置，读出当前结果边界

下表来自 `overnight_summary.csv` 的 `reference_math_*` 组，BF16、相同输入 fixture、每格三轮中位数，`profiled=False`。该组使用参考 Attention、`torch_grouped` experts 与 ownership/source-weight 候选；它是当前测量矩阵中的候选执行路径，不代表每个拓扑已通过完全一致的 HF 全模型验收，也不是生产最优结论。

| 负载 | EP8 | DP2×EP4 | DP4×EP2 | PP2×EP4 | 该矩阵内较快配置 |
|---|---:|---:|---:|---:|---|
| short128 | 112.0 | 197.2 | 304.6 | 100.8 | DP4×EP2 |
| context4k8 | 10.8 | 17.5 | 24.6 | 9.2 | DP4×EP2 |
| mixed64 | 52.2 | 61.1 | 69.2 | 45.3 | DP4×EP2 |

单位为 output tok/s。矩阵还记录了 `arrival64` 和 TTFT/TPOT 分位数；混合请求的平均吞吐不能替代长短请求分别的 P95/P99。以上数据说明在**这组实现与实验设置**里 DP4×EP2 是吞吐候选，并不证明所有模型/并发/质量要求下它都最优。跨拓扑的逐 token 输出存在大量分歧，且 DP4×EP2 还没有与 EP8/PP2×EP4 相同范围的 HF parity 结论，因此在通过相同数值门槛前不能把它定为生产默认。

旧的快数学路径测得过不同的配置排名，但因该路径没有通过最终整模质量门槛，不能与上述参考数学矩阵混在一起挑“最快”。比较时要同时固定路径、拓扑、输入输出 token 数和并发，否则排名会把算子路径变化误认为并行策略收益。

### 4. 通过模型结构解释候选配置

- **EP：** 专家权重分布到各 rank，显存按本地专家数切分；MoE 层需要路由、变长 all-to-allv、专家计算和结果归还。小 batch 或每专家 token 很少时，通信启动、metadata 和多个小 GEMM 可能抵消权重切分收益。
- **DP×EP：** 多个 EngineCore/副本各处理独立请求，副本内部再做 EP。它能增加请求级并行、减少单个 EP 组的服务压力，但要考虑权重副本显存和副本间负载不均。`step_all` 等同步点会被最慢副本拖住。
- **PP×EP：** PP 降低每卡常驻层数，层边界要传 activation。只有有足够独立 microbatch、stage 切分均衡且调度不被阻塞时才可能摊薄 fill/drain。当前 PP worker 串行处理消息，`recv_forward` 有阻塞，已有异步 send / dedicated stream 并未形成稳定端到端收益，也没有完整 DualPipe。
- **TP：** 切分 dense 权重并在层间频繁 collective。大矩阵能把算力分散，但小 batch/decode 时每层通信启动开销相对更明显；是否胜出要由同硬件、同 kernel、同 token 数实测。
- **混合策略：** 先明确每个轴具体切哪组 GPU、各层权重和请求分别驻留哪里，再统计每层通信与显存。只写“TP×EP×PP”不够；不同 group 语义可能完全不同。

### 5. Prefill 和 decode 要分别分析

Prefill 将大量 token 一起计算，dense projection 常是大 M 形 GEMM，Attention 的序列长度也影响计算与 KV 写入。Decode 每个活跃请求每步通常只推进一个 token，M 近似活动 batch，权重读带宽、KV 读取、launch 和小矩阵效率会更突出，可能逐渐接近 GEMV 或小 GEMM。于是可研究按阶段选择 kernel：prefill 用吞吐型 GEMM/融合 Attention，decode 用低 M、低延迟 kernel，并按 batch 与 KV 长度设切换阈值。

当前实验测了不同上下文长度和 batch/并发，不等于已经实现 GEMM→GEMV 的自适应 kernel；本项目没有用现有 trace 证明一个具体阈值，也没有宣称该优化已经带来 tokens/s 收益。若要继续做，应在同一层、同一权重/输入下分别采集 prefill/decode 的 M/N/K、KV 长度、kernel 名、时延与 Nsight Compute 指标，再写独立实现、做数值 parity 和无 profiler A/B。

## 二、现有 Perfetto 轨迹能说明什么

### Attention 与 MoE 时长

最终安全数学路径的 EP8 窗口 `overnight/reference_ep8_window` 来自 `short64` 场景、16 个请求，Profile 仅捕获消息窗口；8 个 rank 有一致时间原点。48 层 annotation 的平均父范围约为 Attention **8.38 ms/层**、MoE **4.07 ms/层**。MoE range 包含路由、dispatch、专家与 combine；Attention 路径使用 `sdpa_reference`，所以它比早期快 Attention trace 昂贵。两组不是同一个 kernel 路径，不能把数值直接解释成长度效应。

早期 EP8 `ep8_window` 中，短请求窗口的平均 range 约 MoE **4.93 ms/层**、Attention **0.26 ms/层**；说明旧快 Attention 路径下 MoE range 是主要热点。4K×8 的 EP/PP trace 缺少完整消息覆盖（`common_complete_messages` 为空），不适合拿来计算 4K Attention/MoE 比例或 pipeline bubble。因此，现有 trace 证明了“算子路径不同会改变时间占比”，但**还没有形成相同数值路径下随长度与 batch 变化的完整 Attention/MoE 动态曲线**。

### MoE 通信 overlap

已核验的 EP8 profile 窗口内，每个 GPU 的计算 kernel 与 NCCL kernel 区间交集均为 **0 ms**；这些 trace 中记录的 kernel 位于相同 CUDA stream，队列顺序本身不会互相重叠。准确说法是“该窗口没有观察到 EP 同卡 compute/NCCL kernel overlap”，不能外推到所有执行模式或所有负载。还没有 Nsight 系统轨迹和链路字节/SM 指标，故也不能断言 NCCL 是带宽瓶颈。

### PP 流水线图

在完整捕获的短负载窗口，stage0/stage1 非 NCCL kernel 的区间交集为：baseline **47.02 ms**（占较小 stage 计算并集约 **19.5%**），optimized **51.80 ms**（约 **22.0%**），dedicated **46.37 ms**（约 **22.7%**）。这是短 profile window 的“两个 stage 同时存在普通 kernel 区间”的比例，不是有效 FLOPs 利用率、气泡消除率或全局吞吐收益。未开 profile 的三轮 PP 消融吞吐变化约为 +0.55%、−0.24%、−0.05%，没有稳定收益。

Perfetto 里判断流水线：同屏对齐 stage0/stage1 的时间轴，按相同 message/microbatch 跟踪 stage0 最后一层、发送 activation、stage1 第一层、返回结果；观察 stage1 首个计算前的等待、stage0 drain 后是否仍有在途工作，分别标记 fill、steady、drain。只看到 CPU `send` 快速返回，不能说 GPU 已重叠；只看到 stage 计算条交叠，不能说 stage 负载均衡。vLLM TP8 当前采集件没有 CUDA kernel/stream/NCCL 事件，只能分析 CPU，不能拿来做 GPU overlap 对照。

## 三、精度校验的方法与原则

### 1. 先区分“数值不一致”与“模型任务准确率”

本项目没有用输出是否相同直接替代任务 accuracy。验证强度分为：算子/组件 oracle、固定前缀 logits、单步 argmax、逐 token 自回归生成、业务数据集任务指标。`384/384` 是 12 条合成输入×32 个 teacher-forced 位置，不是 384 条任务样本，也不是任务准确率 100%。

### 2. 固定一切会改变计算的条件

对比前固定模型文件和 tokenizer、输入 token IDs、position IDs、mask、dtype/autocast、Attention backend、KV/cache 状态、batch 和 padding 形状、并行布局、软件版本与源码 hash。Reference 与被测实现必须接收完全相同的前缀。HF cached generation、HF fresh full-prefix、HF 单请求和 HF batch 也先互相比较，不能默认参考实现不同路径会逐位相同。

### 3. 用 teacher forcing 阻断自回归误差扩散

先取一条确定的 token 前缀，对 HF 与被测引擎逐个计算相同 next-token 的完整 vocab logits。逐位置保存 `argmax`、top-1/top-2 margin、max absolute error、RMSE、top-k 集合和原始 logits。第一处分歧之后的自由生成输入不同，后续 logits 不再是同输入对照，因此先用 forced prefix 定位，再单独做自然生成回归。

比较 greedy winner 必须用 `argmax`。不能把 `topk` 返回的第一个元素当作胜者，因为并列 logit 的次序未必稳定。误差大小和离散 winner 需一起判断：小 logit 差也可能翻转很小的 top-1 margin；较大的误差若远离 winner margin 也未必改变输出。

### 4. 用 EP1、通信 oracle 和逐层 capture 划分责任边界

先跑 EP1：EP1 也偏差时，优先查模型数学、权重、RoPE、Attention、GEMM 或 cache；只有 EP1 正常而多卡偏差时，才重点查分片、路由、通信和归约。对变长 all-to-allv 单独用不同 source/目标长度、空 source 和显式 ID 验证 send/recv splits、route 权重、逆置换与 combine，确认没有重复或丢失 route。

随后在 embedding、Attention projection/output、Router logits/expert IDs、MoE 输出、block、final norm/lm_head 边界捕获张量，从前向开始找第一个不同的层/算子。capture 使用 forward-pre-hook 并在算子执行前复制张量；先证明 instrumentation 本身不会被 residual 原地更新污染。找到首差后，把相同 activation/weight 直接送入算子 replay，改变一个变量（如 GEMM 的 M）验证原因。

### 5. 本次实际定位与剩余问题

已通过相同输入重放确认并修复两处实现根因：

1. **RoPE 表的设备舍入差异：** 旧实现 CPU 生成 sin/cos 再拷到 GPU，和 HF 在 GPU 上 FP32 计算频率及三角函数有细微差异。改为目标设备生成，并比较固定 Q/K 的旋转结果。
2. **EP ownership 改变 router GEMM 形状：** 旧实现先切 token owner 再做 BF16 router GEMM，改变 M 维与累加路径，微小 logit 误差可改变离散 top-k。改成完整 replicated input 上算 router，再只派发 owner tokens；同时对空 source、变长 split、TP2×EP2 做分布式 oracle。

仍存在的跨 batch GEMM 形状敏感性：1024-token、batch=1 vs 3 在 L0 `o_proj` 首先可见差异，2,097,152 个元素中 670,271 个不同，max abs 0.00390625、RMSE 3.78e−5；重放相同权重/输入能复现 BF16 `F.linear` 差异并改变下一 token。47-token、batch=1 vs 8 在 L0 `q_proj` 首差。`batch_execution_mode=per_request` 在三个受控小场景输出逐元素相同，但失去批量 GEMM 融合；短投影微基准约慢 3.8×，不能当默认性能修复。严格 batch-invariant 的全模型解法仍未完成。

在限定路径下，EP8 与 PP2×EP4 各自对 12 条合成输入的 384 个 forced-prefix 位置与参考 logits 逐元素相同；单请求自然生成 12/12 全文一致。batch rollout 与参考全文一致为 5/12，首个 winner 变化会在自回归中放大。必须同时报告这些通过和未通过，不把某一组 384/384 扩大解释为全模型质量保证。

详细原始过程、旧失败样例和边界见[精度问题排查方法论](精度问题排查方法论.md)、[正确性与消融复核](056正确性与消融复核.md)。

## 面试回答示例

**问：你怎么系统地判断哪种并行最好？**

> 我先定义优化目标，比如最大化满足 TTFT/TPOT/P99 的输出 goodput，再按输入/输出长度、并发、到达模式、prefill/decode 比例构造固定 fixture。所有 topology 用相同模型、dtype、输出 token 数、batch/token budget，吞吐与 profile 分开采。trace 先过 rank、层、消息和时钟完整性检查，再按 GPU/stream/层/Attention/MoE 拆 kernel 与 NCCL 活动；PP 看同一 microbatch 的 stage 依赖，MoE 看每专家 token 分布与 dispatch/compute/combine，通信 overlap 只按同一设备的 CUDA 区间交集判断。然后用无 profiler 重复吞吐与尾延迟筛出 Pareto 候选，最后跑相同路径的 HF logits、通信 oracle 和自然生成质量验证。目前我能给出的结论是本组候选吞吐矩阵 DP4×EP2 领先，但还没有完成相同范围的拓扑质量验收，所以我把它叫候选，不说全局最优。

**问：你从 trace 真正找到了什么？**

> EP8 的一个短请求 profile 中，旧快 Attention 路径的 MoE layer range 约 4.93 ms，Attention 约 0.26 ms，MoE 是明显热点；但参考数学路径下 Attention 约 8.38 ms、MoE 约 4.07 ms，说明优化算子本身会改变占比，不能跨实现拼一条动态曲线。短负载 PP 窗口里 stage 计算区间有约 19.5–22.0% 的交叠，同卡 compute/NCCL kernel 交集为零，端到端 PP 消融没有稳定加速。4K trace 的完整消息覆盖不足，我不会把它用于长度趋势结论。下一步需要在同一后端下补齐长短/不同 batch 的完整 profile，再用 Nsight 采硬件计数确认原因。

**问：精度分歧怎么排？**

> 我先锁定同一 token IDs 和执行形状，用 teacher forcing 比完整 logits，避免自由生成第一次分歧后输入变掉；然后对照 HF 单请求/批处理，跑 EP1 和 all-to-allv oracle，再用 forward-pre-hook 找首个不同的层，并把该层的同一 activation/weight 做单算子 replay。这样确认了 CPU 预计算 RoPE 舍入和 EP ownership 改变 router GEMM M 维两个根因并修复。之后又发现 L0 BF16 q_proj/o_proj 对 batch M 形状敏感；per-request 只在有限场景通过，仍不是全局修复。结果会按组件、forced logits、连续生成分别报告，不把 token 一致率说成任务准确率。
