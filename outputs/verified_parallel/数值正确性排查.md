## 20:40 新增结论：把串行化做成显式保守路径

`v9/config.py` 新增 `batch_execution_mode`，默认 `batched`；`per_request` 会在每个 worker 内按请求分别执行，以固定单请求 GEMM 形状。它不是把 EP/PP 通信改成定长，也不是性能优化。

- EP8、47-token、batch=8、`per_request`：L0 投影/Attention/router/MoE 和输出头捕获逐元素相同，两步输出相同。
- EP8、1024-token、batch=3、`per_request`：L0/L1/L2/L47 的选定边界逐元素相同，两步输出相同。
- EP8、1024-token、batch=3、`batched`：L0 `o_proj` 首差 670,271/2,097,152，max abs 0.00390625，第二输出 token 改变。
- PP2×EP4、47-token、batch=3、`per_request`：stage0 L0 与 stage1 L24/L47 的 Attention/MoE/block 及 lm_head 逐元素相同；远端 4 项 CPU 回归为 `OK`。

因此当前可用的准确性策略是：默认批处理用于吞吐，但质量回归、定位和对跨 batch 复现有硬要求的场景可显式选择 `batch_execution_mode=per_request`。不能把它扩大成任意长度/并发的证明；全局方案仍应优先研究固定 tile、FP32/更稳定累加、路由 margin 监控和逐层质量门槛，并测清吞吐代价。

## 当前能证明什么

本轮发现的关键问题是：**同一输入在不同并行配置下产生不同 greedy 输出，不能直接把这些配置的速度当成质量已经等价的性能成绩。** 为定位它，分别控制了路由精度、算子舍入、Attention 路径、专家实现后端和 GEMM 形状。

| 验证范围 | 结果 | 结论边界 |
|---|---|---|
| EP1，reference math、BF16 router logits、SDPA reference | 24/24 固定前缀 next-token 与 HF 相同 | 只有三条输入、每条八个前缀 |
| EP1 完整输入逐层捕获 | embedding，以及 L0/L1/L2/L47 已捕获边界误差为零 | 不等于全部层、任意输入、decode cache 均已验收 |
| EP8，native backend，仍复制所有源路由 | 21/24 相同 | native API 本身没有消除全模型偏差 |
| EP8，native + ownership + source weight，相同 reference math | 24/24 相同 | 有限固定前缀测试，不是任务质量基准 |
| EP8，loop + ownership + source weight，相同 reference math | 24/24 相同 | 表明本组改善并非必须依赖 native backend |
| 专家本地 replay，相同输入/路由/矩阵形状 | loop/native 对 HF grouped 误差为零 | 是局部受控实验，不是全模型认证 |
| 变长 EP / TP2×EP2 oracle | 空 source、不同 source 长度、两种权重位置均通过 | 数学组件通过，不代替真实模型检查 |

较早吞吐矩阵使用默认数学路径；上述 reference 配置通过的小样本不能替那些矩阵背书。新机扩大验证实际为 EP1 44/48、EP8 单独请求 46/48、EP8 批量和 PP 单独/批量均 44/48。连续生成 EP8 为 7/12 exact，PP 单独为 6/12；PP 批量因显存预算失败，不能算通过。这里既包含 fresh-prefix 与 cached-reference 的执行形状差异，也可能包含实现偏差；需要 HF 自身对照及逐层验证，不能先统一归因 BF16。

## 为什么先做 teacher forcing

自由生成只要一个 token 不同，之后输入前缀就不同，后续差异会混合“实现偏差”与“输入已经变化”。本轮先让 HF 生成 continuation，再把每个相同前缀分别输入两套引擎，比较其下一 token 的完整 logits。

除 top-1 相同率，还保存最大绝对误差、RMSE、概率分布 total variation、top-10 交集、HF 前两名 margin。`2×最大 logit 误差 < HF margin` 是 top-1 稳定的充分条件；条件不满足不能直接推断输出一定错误。

本轮样本是合成文本，不是质量评测集。固定前缀匹配也不能替代多轮对话、任务准确率、长上下文质量和多模态评估。

## 第一层误差如何被复现

默认 EP8 的 Attention 输入在八个 EP rank 上相同，但每个 rank 都发出完整 token 的 top-k routes。对于 T 个输入、每 token k 个专家，全组发送 **8×T×k 条 route**；各专家会收到八份相同的输入行。每个 source 最终只取回自己的结果，数学上没有直接少项，但改变了专家 GEMM 的 M 维和计算成本。

用相同的 HF 首层输入、固定 expert IDs 和权重，只把输入复制 1/2/4/8 份：

| 复制倍数 | L0 MoE 与单份 HF 的最大误差 | RMSE |
|---:|---:|---:|
| 1 | 0 | 0 |
| 2 | 0.0001220703125 | 7.8087e-7 |
| 4 | 0.00048828125 | 2.2662e-6 |
| 8 | 0.00048828125 | 2.5078e-6 |

复制八份的结果恰好复现原 EP8 首层 MoE 的误差量级与 RMSE。在“同一复制倍数、同一输入和路由”的 HF grouped 对照中，loop 与 native replay 误差均为零。因此，首层差异有一条受控的形状解释，而非只能猜测 NCCL 算错。

**这还不能解释所有深层分歧。** MoE router 是离散 top-k；上游微小变化可能改变 expert 选择并继续放大。旧 EP8 深层差异明显，不能统一贴上“正常 BF16 误差”标签后跳过验证。

## 做了哪些修改

1. 保留可切换的 reference math 路径，显式控制 RMSNorm、RoPE、激活的中间舍入；router 可按模型 dtype 计算 logits，再做 FP32 softmax。
2. 加入 `sdpa_reference`，用独立 Attention 对照隔离 paged/chunked Attention 与 MoE，代价是它不是生产性能上界。
3. EP replicated-input ownership 模式把 token 行分给不同 source，只派发一份 route，最终 all-gather 恢复复制输出。这需要组内输入相同的前提，不能直接复用到 Attention-DP 输入各异的布局。
4. source 已持有每条 route 的权重，因此可让目的端返回未加权 expert 输出，再由 source 按原 route 乘权。少一次权重 metadata all-to-all；默认仍保留原路径作为对照。
5. 抽出统一 `compute_sorted` 接口，loop/native 共享 dispatch、排序和 combine。native 使用已有 PyTorch grouped API，没有本轮新写 CUDA kernel。

ownership 的 all-gather 为统一行数可能补至多 EP−1 行尾部；这和专家按最大 capacity 补 padding 是两件事。专家 all-to-allv 的发送仍由实际 route counts 决定。

## 为什么这也是性能项目的关键部分

消除重复 route 是一个清楚的动机，但旧端到端 ownership 实验反而变慢：额外 gather、token indexing 和小 GEMM 形状可能吃掉收益。需要把“减少了多少 route”“是否保持数值语义”“最终是否提速”分别测量。

面试中可以解释：我先验证数据所有权，发现重复路由不仅浪费通信/计算，还会改变低精度 GEMM 的形状；随后用受控 replay 复现首层差异，再做有限的全模型固定前缀验证。**这是一条可检查的诊断证据链，不是宣称发明了 EP 或已经超过 vLLM。**
