# 量化、混合精度与投机解码复盘

## 结论

当前 v9 serving runtime 的主路径是 BF16。RTN INT4、混合精度和投机解码的结果来自旧实验日志，不是本轮 matched 8×A800 性能矩阵的一部分，也没有和当前源代码建立完整 hash 对应。现有结果足以说明旧原型还不能作为性能成果汇报：量化省权重空间但明显变慢、输出分歧较大；投机解码在三个短样例上都没有加速。

## 量化

旧日志 [quant2.log](../quant2.log) 记录了 group=128 的 RTN W4：BF16 权重约61.07 GB，量化后约16.69 GB，压缩3.66倍。但这个实现先反量化为 BF16 再走常规 GEMM，BF16 测试约19.7 output tok/s，W4 约3.3 output tok/s。五条短输出与 BF16 的 token 对齐总分歧率为45%，第一个样例在生成第1个 token 就出现分歧。

这表示它取得了权重存储收益，没有取得有效的推理加速或可接受的质量证据。反量化产生的临时 BF16 权重、额外读写和普通 GEMM 会抵消低比特权重的带宽收益。仓库里的 Triton `dequant_gemm` 是独立原型；当前 MoE serving 路径没有用一个经过端到端验证的融合 W4 kernel 取代 BF16 expert GEMM。

## 混合精度

[mixed2.log](../mixed2.log) 记录 BF16 约61.07 GB、混合权重约18.03 GB，日志给出的压缩比为3.39倍；速度从17.55降至2.94 output tok/s，日志报告的 token agreement 为73.2%。日志没有保留足以复现的逐层精度策略、量化校准集、完整输入、代码 hash 和指标计算定义，所以这些数只能作为旧原型的负面诊断，不能与本轮 BF16 并行矩阵做横向比较，也不能据此证明混合精度质量。

下一轮应固定并记录逐层精度策略、校准集许可、量化格式、kernel backend、KV cache dtype、相同输入与输出 token 数；先测质量和峰值显存，再比较预填充/解码吞吐与长尾。低比特权重只有被融合 kernel 直接消费，才有机会把带宽收益转成速度收益。

## 投机解码

[spec.log](../spec.log) 保存了三个短 prompt 的旧原型结果。输出文本均与 target-only 对照一致，但接受率分别为1%、40%、0%；耗时分别是4.2→27.6秒、1.5→11.1秒和4.1→22.7秒。样例数很小，不能推导生产收益；但这些数据明确显示该原型没有加速，不能把“输出一致”当成实现有效。

当前 `engine/` 推理主路径没有 draft model、批量验证、KV 回滚与拒绝采样集成，也没有 speculative decoding API。要重新做，应先让 target-only 与 speculative 的 token/logits 语义一致，再测不同 draft/target 模型组合和输出长度下的 acceptance length、额外 forward 成本、KV 管理成本、TPOT 与吞吐。只有接受的 token 足以摊薄 draft 和 verification 开销时，投机解码才会变快。

## 面试时的准确说法

“我做过一个 RTN W4 和投机解码原型，但测到的结果是权重压缩没有换来速度，W4 生成也有较高 token 分歧；投机样例接受率低且更慢。我没有把它们集成到当前 serving runtime，也没有把旧日志和本轮并行结果混用。下一步会先采用受支持的低比特 fused backend，固定公开许可的校准/评测数据，再用相同输入做质量、显存、prefill、decode 和长尾对照。”
