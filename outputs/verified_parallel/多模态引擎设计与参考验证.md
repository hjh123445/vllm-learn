# 从文本 Thinker 到多模态推理引擎

本轮已用 HF 加载 Qwen3-Omni 的预训练 encoder 与 Thinker，跑过图片、音频和视频输入。**自研引擎尚未接入媒体请求，支持该模型的文本权重不等于支持其多模态接口。**

## 已做的真实验证

输入均自行生成，未读取服务器上来源不明的数据。原始记录见 [media_probes.json](overnight/hf_reference/media_probes.json)。

| 输入 | Processor 输出的主要张量 | Thinker 输入长度 | 单次 forward 时间 | 范围 |
|---|---|---:|---:|---|
| 224×224 图片，白底红色矩形 | pixel_values=[196,1536]，image_grid_thw=[1,3] | 64 | 2.403s | Processor、真实视觉 encoder、Thinker |
| 1秒440Hz合成音频 | input_features=[1,128,100]，feature_attention_mask=[1,100] | 28 | 0.297s | Processor、真实音频 encoder、Thinker |
| 4帧合成视频 | pixel_values_videos=[1152,1536]，video_grid_thw=[1,3] | 303 | 9.508s | Processor、真实视觉 encoder、Thinker |

三者 logits 均有限值。这些是单次功能 probe，初始化、首次 kernel 使用和不同媒体形状会影响时间；不能用这些数字比较模态吞吐，也不能证明模型理解质量。当前 probe 只做 forward，没有验证 Talker 流式音频生成。

`196`、`1152` 是 processor 展开的 patch 行数，`1536` 是该张量每行的 patch 特征长度，不能直接叫作最终 LLM hidden size。LLM token 长度也不能拿原始 patch 行数直接替代；应以 encoder 合并、投影和占位符展开后的实际输入为准。

## 与纯文本引擎的共同部分

媒体经过 encoder、投影、位置编码和 embedding 插入后，Thinker 的 decoder 仍要执行 Attention、MoE、KV 管理、continuous batching、采样与并行通信。因此原有 decoder 优化可以复用，但其前提是输入 embedding、position IDs 和 KV 逻辑正确。

不能只把图片路径塞进 prompt 字符串。tokenizer 不会自动执行视觉或音频 encoder，也不会替引擎分配媒体计算和显存。

## 必须增加的路径

```text
请求：文本 + 媒体 + 时间信息
  → 校验、解码、抽帧/重采样、processor
  → 媒体任务队列及预算
  → vision/audio encoder + projection
  → 媒体占位符与 embedding 对齐、MRoPE/时间位置
  → Thinker prefill → paged KV decode → 文本输出
  → 若需语音输出：额外 Talker/codec 与流式输出调度
```

| 子系统 | 纯文本常见假设 | 多模态需要增加 |
|---|---|---|
| 请求协议 | input_ids、sampling params | 媒体对象、模态、帧率/时间戳、采样率、媒体 ID |
| 预处理 | tokenize，长度主要由文本决定 | 解码、抽帧、resize、音频特征；CPU 时间与内存预算 |
| 输入表示 | token embedding lookup | 指定位置替换为 encoder features；数量和顺序必须严格匹配 |
| 位置 | 一维 token positions | 视觉时空坐标、MRoPE、视频时间；decode 位置偏移也需一致 |
| 调度 | prefill/decode token budget | encoder token/patch budget、最大像素/帧数/音频时长、encoder 与 decoder 抢占 |
| 缓存 | 文本 prefix 与 paged KV | media hash、processor 版本、encoder feature cache；区分 features 与 KV |
| 并行 | decoder TP/EP/PP | encoder 放置/切分、features 传输、stage0 额外负载 |
| 可观测性 | tokenization/prefill/decode | media decode、encoder、feature handoff、LLM prefill 的独立范围 |

## 建议接入顺序与验收标准

先实现单张图片到文本输出的离线请求。请求中携带只读媒体描述和 feature 引用，模型入口接受可选 `inputs_embeds`/媒体位置元数据；不要把媒体 encoder monkeypatch 到每层 Attention。先对齐 HF processor 的 tensor、encoder feature、embedding 插入后的首层输入和 logits，再做连续生成与不同图片长度的 batch。

第二步加入视频帧和时间坐标，第三步接入音频及音视频时间对齐。不能把视频当成无时间信息的图片列表后声称完整复现模型；音频流式窗口也需要独立的状态与延迟定义。

进入服务模式前至少验证：媒体占位符数量不符时明确报错；图片和纯文本请求混批；prefill chunk 边界落在媒体区间时行为正确；prefix cache 不跨不同媒体错误复用；取消请求回收 encoder features 和 KV；媒体异常不使所有 worker 永久等待；PP stage0 的 encoder 工作不会被重复执行。

## 视频搜索岗位该怎么分析

视频搜索中，帧数、分辨率和音频时长决定 encoder 负载和 LLM 的有效输入长度。只报告生成 tok/s 会掩盖用户等待媒体处理的时间，应同时报告媒体预处理、encoder、首 token、后续 token 以及端到端 P95/P99。

可验证的问题是：在固定质量约束下，抽帧策略、encoder 缓存和 encoder/decoder GPU 放置如何降低 TTFT 长尾？实验应固定公开数据版本和视频长度分布，按帧数/时长分桶，并分别画 encoder 与 decoder 时间线。当前合成 probe 为后续接入提供参考张量，尚不能回答视频检索业务效果。

公开数据也需要保存 dataset manifest：下载来源、版本、许可、样本 ID、媒体权利与处理方式。未知服务器目录只说明“有文件”，不证明允许使用；本轮没有将其作为实验输入。
