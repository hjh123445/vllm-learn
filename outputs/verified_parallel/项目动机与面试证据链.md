# 为什么做这个项目：从“实现框架”转向“用证据解决 MoE 推理问题”

> 研究对象：Qwen3-Omni-30B-A3B 的 thinker 文本路径；硬件：单机 8×A800。
> 本文把“已验证事实”“待验证假设”和“后续能力”分开。夜间新实验的最终数字以原始记录及汇总报告为准。
>
> 2026-11-04 新机扩大验证已完成：组件 oracle 通过，全模型 48 个固定前缀和连续生成仍有分歧；24/24 小样本结论已被扩大范围限定。见[056复核报告](056正确性与消融复核.md)。尚不能宣称质量等价下超过 vLLM。

## 面试官问：为什么做，为什么不用 vLLM？

可以这样回答：

“生产部署我会优先选择 vLLM 等成熟框架。这个项目的目的，是掌握性能问题从调度、张量布局、通信到 GPU 执行的完整因果链。我的问题是：在固定 8 张 A800 上部署一个稀疏 MoE，怎样在显存约束下选择 EP、PP×EP 或 DP×EP，并解释吞吐和尾延迟为什么变化？我搭了一个足够小、能逐层观察的推理引擎，保留相同模型和输入，逐步验证数值正确性、定位重复工作、做并行策略消融，再用多 GPU trace 检验解释。项目价值是我能定位和修正具体瓶颈，能够说明优化在哪些条件下成立。”

不要回答“vLLM 不支持这些，所以我实现了”。vLLM 已有成熟的调度、分页 KV、并行通信、融合专家算子及多模态基础设施。这个项目不能拿功能列表证明创新，也没有足够证据声称比 vLLM 快。

## 最值得深入讲的点：EP 的数据所有权

### 具体问题

当前引擎让同一 EP 组的 attention rank 处理相同 token batch。专家权重虽然按本地专家数分片，但每个 EP origin 都会把相同 token 的 top-k 路由发到专家 owner。这样能够得到各 origin 所需的完整结果，却会把同一条专家分支计算 EP 次。

“专家权重已经分片”与“专家计算没有重复”是两件事。张量形状正确、结果正确，也不代表通信量和计算量合理。这比“我用了 all-to-allv”更值得面试展开。

### 可证伪假设

设同一 EP 组包含 P 张卡，输入有 T 个 token，每个 token 激活 k 个专家。

- 复制输入的原始实现：全组实际接收并计算的 route 数约为 **P×T×k**。
- token ownership 方案：每个 origin 只负责一段 token，预期全组 route 数为 **T×k**。
- 为保持后续 attention 接口不变，专家 combine 后还需要把不同 origin 的输出 all-gather 回复制布局。

这不意味着端到端一定快 P 倍。attention 仍复制；all-gather、多次 counts 同步、路由排序、Python 专家循环、小 GEMM 都可能成为下一瓶颈。

### 实现与边界

候选实现由 `VLLM_LEARN_EP_SHARD_REPLICATED_INPUT=1` 开启，默认保留旧路径用于对照。核心是不修改通用变长 dispatch/combine 的语义：它仍允许不同 source 的 token 数不一致、允许空 source。上层只在“EP 组输入及 token 顺序完全一致”的条件下切 ownership，并在输出处恢复复制布局。

all-to-allv 的 activation 按实际 route 长度传输，不需要专家 capacity padding。恢复输出采用等长 all-gather，因此只在 ownership 的最后边界补行，全组最多 P−1 行。这与把每个专家都填到热点专家容量不是同一种 padding。

不能把这个包装层直接用于 attention-DP：不同 rank 若本来持有不同请求，再切一次相同索引会丢 token。需要显式的数据布局契约，而不能只看 `ep_size > 1`。

### 需要什么证据才算解决

1. **算子 oracle**：TP2×EP2，FP32/BF16，T=0/1/3/8/17，优化前后数值容差内一致；全组 route 计数恰为 T×k。
2. **端到端正确性**：相同输入的 greedy 序列比较；不同 GEMM 形状导致 BF16 分歧时，进一步比较逐步 logits、top-1/top-2 margin 和独立 HF 参考，不能用“浮点误差”一句话略过。
3. **性能对照**：APC 关闭、BF16 eager、相同 token IDs/输出长度/预算；短64、短128、1K、4K、混合长度，至少三轮。初始化和 profile 不计入吞吐。
4. **机制证据**：原始专家计数、每层通信量、GPU kernel 次数与时间、host 同步、all-gather 代价。减少 route 的直接证据比只看 tok/s 更强。
5. **负面结论**：如果小批 decode 没变快，要解释新 collective、极小 GEMM 和 host 开销；不能只展示有利 shape。

当前这是一项已写入代码、正在验证的优化候选。未完成上述验证前，不应写成“已优化 EP 并取得若干倍加速”。

独立源码核查还发现 router 数值口径需要实测：本项目 `F.linear(x.float(), weight.float())` 用 FP32 计算 logits；当前参考的 Transformers 5.12.0 Qwen3-Omni thinker router 使用输入/权重 dtype 的线性计算，再以 FP32 做 softmax。BF16 近似分数可能改变 top-k 选择，因此重复 greedy 一致不能消除这个差异。必须结合参考版本、逐步输出、路由 logits 与 top-k margin 评估，不应在未验证时称逐位对齐 HF。

## 第二个深入点：PP 调度必须用 trace 证明

### 问题

PP 减少每卡层数和 KV/权重占用，却增加 stage 间依赖、activation 传输和填充/排空气泡。小并发 decode 的计算很碎，microbatch 切得越多也可能越慢；异步 API 不等于 GPU 上发生重叠。

项目已有 forward-only microbatch、有限 lane/credit 和通信 stream 的原型，但不能因此称为 DeepSeek DualPipe。训练 DualPipe 依赖 forward/backward、通信与计算的共同调度；当前没有反向、权重梯度和优化器步骤。这里没有“只差加一个开关”的 zero-bubble。

### 假设与验证

- 假设 A：增加在途 microbatch 能让下游 stage 在上游计算后续 microbatch 时工作。
- 假设 B：更大 microbatch 减少专家小 GEMM 和消息开销，但会降低流水并发。
- 假设 C：长 prefill 与 decode 的最佳配置不同，混合长度会放大 head-of-line blocking。

消融维度是 microbatch token budget 32/128/512、lane 1/2、baseline/optimized，固定总请求与 scheduler token budget。先比较相同输出，再比较三轮吞吐、TTFT/TPOT 分位数；单独采 trace 验证不同 stage、microbatch 和 CUDA stream 是否真正交错。

已有旧负载中，PP optimized 相对 baseline 仅约 +0.55%/−0.24%/−0.05%，没有稳定收益。这个负结果本身有价值：它否定了“把 send 变成异步就能提升吞吐”的想法。更完整的长输入消融正在补充，不能提前解释成已经消除了瓶颈。

## 第三个深入点：把“最优配置”定义成负载与 SLO 的函数

“PP×EP 最先进，所以最好”不是结论。需要同时考虑：

| 方案 | 节省什么 | 支付什么 | 可能适合什么场景 |
|---|---|---|---|
| EP8 | 每卡只存本地专家权重 | MoE dispatch/combine；当前 attention 复制 | 单副本、低并发延迟；需检验小 GEMM 与路由开销 |
| PP2×EP4 | 再按层切权重、KV、激活 | stage 边界与 fill/drain；每 stage 的专家分片更少 | 显存或跨节点约束更强、可提供足够在途工作 |
| DP2×EP4 | 独立请求队列与 KV 池 | 多份非专家权重；请求分配、慢副本等待 | 高并发吞吐；需控制长请求导致的副本倾斜 |

比较必须报告固定 8 卡 aggregate throughput，也要看每请求延迟。DP 是推理副本，每个副本有独立 EngineCore；训练 DDP、ZeRO-1 不属于这里的实现。当前 frontend 还有 step join，不能称为成熟异步服务系统。

## 与 vLLM 相比，自己特别的点应该怎么说

可以说：**“我把一个可复现、可解释的性能问题完整走通了。”** 具体包括数据所有权的检查、变长通信的正确性、负载驱动的并行选择、可读的多 rank 层级 trace，以及失败实验的保留。这些体现自己的系统理解和工程能力。

不宜说：实现了 vLLM 没有的 EP/PP、达到零气泡、复现完整 DualPipe、已支持全模态、端到端超过 vLLM。这些都需要额外证据，其中部分与当前实现事实不符。

如果 token ownership 优化最终通过验证，可以把介绍集中到“识别并消除复制输入下的重复 MoE route”，给出全组 route 数从 P×T×k 到 T×k 的机制证据，再报各负载的端到端收益和代价。若验证失败，先解释失败原因并保留负结果；不能为了讲故事把未通过的候选说成完成。
