## 结论

1. 当前代码支持 EP、PP×EP 和进程级 DP 推理。三者各有工作负载范围，不能称某一种对所有视频搜索流量都是最优。
2. 同口径原始结果中，EP8、PP2×EP4 optimized、DP2×EP4 的短文本8请求分别为73.39/50.78/65.11 output tok/s；long16分别为90.63/49.57/94.61；short64分别为443.36/111.07/462.79。三者使用完全相同的输入 token 数组，每配置三轮。DP 的8张物理GPU分成两份独立模型副本，每副本 EP4。
3. DP2×EP4在64请求下比EP8吞吐高约4.4%，但DP benchmark当前只测整批wall time，没有逐请求TTFT/ITL；EP8的TTFT P95为约0.594s，不能用本轮数据与DP做TTFT对比。DP每副本只跑EP4，并没有像单副本EP8那样让全部专家分片在8卡间共同分布。
4. 本轮没有证据证明 PP 异步模式稳定改善性能。相同 PP 原始三轮结果中，optimized 相对 baseline 在 short8/long16/short64 分别约 +0.55%/-0.24%/-0.05%。单条长序列不能在同一 scheduler step 内拆成多个 PP microbatch，PP 的 fill/drain 与串行 worker 仍然显著。
5. TP×EP all-to-allv 组件数值检查在四张 A800 上通过，覆盖一个 EP source 发 0 token、不同 source 长度、FP32/BF16 和 top-k combine；最大误差记录见 [数值校验日志](tp2ep2_numerical.log)。这是合成 MoE 组件 oracle，不等价于完整模型对 HF logits 的精度认证。
6. CPU 线程过度订阅会显著拖慢初始化：早期 DP2×EP4 默认环境约 410–413 秒；显式 `OMP_NUM_THREADS=4`、`MKL_NUM_THREADS=4` 后约 34.65 秒。将默认线程控制同步到 worker/core 后，在三项线程变量均未设置的情况下再次实测为 34.55 秒，short8、long16、short64 correctness 均通过，见 [默认线程验证](dp2ep4_default_threads/) 和 [日志](dp2ep4_default_threads.log)。独立 TP2×EP4 run 同一显式限制下约 22.35 秒；不同拓扑不作直接速度比较。
7. DeepSeek DualPipe、zero-bubble PP、同卡多个逻辑 stage、完整 vLLM virtual engine、本项目多模态输入、speculative decoding 均未实现。无效的固定 microbatch/zero-bubble 选项现在会明确报错。

### 结论如何用于选型

- 单副本需要让 128 个专家分散在所有 8 卡、追求短 prompt TTFT：当前数据支持先测 EP8。
- 大并发吞吐优先且每请求可路由到独立副本：DP2×EP4 值得优先测；代价是副本内并行规模减小，DP 调度器当前 step 聚合仍等所有副本。
- PP2×EP4：当单副本 EP8 的权重/KV/激活预算不合适，或具备显著更长的计算窗口和更好的 stage balance 时才有理由选。本轮在 16-token 输出、短输出的小负载下没有吞吐依据支持它。
- 生产结论要用目标服务的请求到达分布、prompt/output 长度、SLO、流量并发、故障重启和拓扑重测。当前只有合成负载，非视频搜索用户流量。

## DP 是什么：不是训练 DDP

`DPFrontend` 为每个数据并行副本启动一个独立 supervisor 进程；该进程内部启动自己的 EngineCore/worker 子进程，物理 GPU 列表彼此不重叠。每份拥有 scheduler、权重副本、KV cache 与内部 TP/EP/PP group。请求经 round-robin 或显式 dp_rank 路由到一个副本，生成期间不迁移 KV cache。DP 副本间不传模型 activation，也不做梯度 all-reduce。这里的 DP 是 inference data parallel replica，不是训练 DDP。

当前离线 `step_all()` 同时驱动各副本，但 join 等待慢副本；因此它并不是无等待的独立忙循环。生产版要使用异步事件/完成队列、按负载路由、健康检查、超时与失败隔离。

## EP 语义与负载长尾

每个 rank 只持本地专家权重，专家参数首维是 `E_local = E / EP`；EP8 下 16 个专家/rank，PP2×EP4 下 32 个专家/rank。Router 保留全局专家 logits 是必要的路由信息，并不意味着专家权重也全量复制。

数据流是 route flatten → 按 EP destination 排序 → 交换每个 peer 的 count → `all_to_all_single` variable splits 发送 token/metadata → 本地专家计算 → all-to-allv 返回 origin → 恢复 route 顺序 → FP32 top-k 累加 → 若 TP>1 再对 TP partial 做 all-reduce。因为 combine 已把贡献送回 origin token rank，不应再对 EP 做结果 all-reduce。各目的 rank token 数允许不同；没有全局 max-token padding。`send_counts.tolist()` 仍产生 GPU/CPU 同步；route metadata 和 payload 分多个 collective；专家 GEMM 仍有逐专家 Python 循环，这些是主要 kernel/metadata 优化空间。

本轮 expert counter 最初包含模型测显存 warmup，不能用来讲生产负载热点。代码现在在请求 trace 前重置统计，`ep8_expert_profile` 是 request-only 的合成 long16 profile。需要用分布更广的公开许可语料和更长时间序列重复采样，才适合讨论 persistent hot expert、负载 CV 和 tail latency。

## Trace 场景、瓶颈与如何读

详细文件目录及解释见 [TRACE阅读指南.md](TRACE阅读指南.md)。本轮提供：

1. **之前单卡 trace**：`../qwen3_omni_trace.json` 是 TP=EP=PP=1 的 48 层文本 decode，单 worker/单 CUDA stream，MoE annotation 平均约 2.201ms/层、Attention 约 0.391ms/层。它不是 PP trace。
2. **当前 EP8 trace**：8 个 A800 rank；展示了每层 attention/MoE、NCCL all-to-all 和真实 kernel。采样区间很短，profile 期间运行态和普通吞吐分开。
3. **当前 PP2×EP4 trace**：stage 0 是 GPU0–3、global layer 0–23；stage 1 是 GPU4–7、layer 24–47。每张设备都记录 rank、EP rank、CUDA stream、MB id、Attention/MoE；raw Perfetto JSON 和逐 GPU/stream SVG 已保存。
4. **prefill PP baseline/optimized**：同输入采样位于 `pp_prefill_baseline/trace/` 与 `pp_prefill_optimized/trace/`。文件覆盖rank0–7，但 baseline的rank6没有kernel；两者都只采到部分层（stage0约L0–18，stage1约L24–40），不是完整prefill。输入仍是196–197token，不能称真正长上下文。另一个 `pp_prefill_baseline_full/trace/` 缺少rank2且rank0有`.partial`，不用于跨设备对照。文件齐全不代表CUDA采样完整。
5. **主机 pipeline trace** 用 `perf_counter` 单调钟，CUDA trace 有 `baseTimeNanoseconds`。同一类 trace 可跨 rank 比较；主机 pipeline JSON 与 CUDA CUPTI 时间戳不是同一时钟，不能直接拼成共同物理时间轴。

GPU kernel union/span 是当前采样窗口内的时间区间覆盖率，不是 SM occupancy、active warps 或有效 FLOP 利用率。NCCL kernel interval 可能包含等待/轮询；NCCL/层 annotation 会嵌套。所有 range duration 简单求和都会双重计数。CUDA profiler 使用 PyTorch/CUPTI，包含 CUDA kernel、memcpy/memset、NCCL kernel 和 stream ID；不是 Nsight Systems 的完整硬件 counter/调度分析。

## 多模态差异与公开数据边界

当前 `v9/models/qwen3_moe.py` 是文本 thinker；loader 跳过 vision/audio tower，入口只接受 tokenizer 后的文本 token。模型权重有 Qwen3-Omni 多模态组件，不表示引擎已有多模态 serving。

视频搜索需要端到端处理 video frame/timestamp、图像 patch、音频/ASR segment、媒体 processor 和 modality token/embedding 对齐；Omni thinker 有 vision/audio tower、projector、音频编码路径、时空 MRoPE 与 multimodal position。视觉数据可能把少数帧展开成许多 patch token，音频以不同时间分块，prompt token 预算、KV cache、prefill 长尾、CPU 解码/预处理和 P2P payload 都会变化。模型还可能有 Talker/audio generation 路径，不等同于当前文本输出 head。

合理落地次序：先接入官方 HF processor 和单卡视觉/音频 embedding parity；加带 timestamp 的 video frame sampler 与音视频对齐；定义 request schema、media payload 生命周期、CPU/GPU preprocessing queue；再做 EP/PP/DP 的模态负载与时延分析。先用自己生成或许可清楚的小型样例验证。远程机器中“有某目录/数据集”不构成公开授权，本轮未扫描和读取这些数据；在核实数据集页面、数据版本、媒体版权、用途和再分发许可前，不用它们做实验。

## 代码审计与未完成项

- `v9/layers/moe.py` 的 Python expert loop、小 GEMM、scatter，COUNT/ID/weight 的多个 NCCL collective 与 `.tolist()` 同步，是明显低于 vLLM FusedMoE/DeepEP 的地方。下一步先做 profiler 归因，再比较 grouped GEMM、Triton/CUTLASS/MoE kernel；通信方案先基准 NCCL all-to-allv，再考虑 DeepEP/拓扑感知 backend。
- EP rank 复制同一份 token 输入和 Dense Attention，router 与 attention 有冗余。这不等价于成熟的 Attention-DP+EP 设计。
- PP 目前一进程一个 stage、worker 一次处理一条消息、recv 阻塞等待 shape/payload、没有常驻 receive queue；同一请求不能在 step 内切 token chunk。普通 DP/PP step 仍有同步等待。
- `pipeline_lanes` 和 `VirtualEnginePool` 是有限的 microbatch lane / in-flight 记账，不是 vLLM 完整 virtual engine（没有其请求/KV 生命周期、抢占和异步调度语义）。Topology planner 能表达同卡多 stage，但执行器会明确拒绝它。
- `build_forward_schedule()` 仅为 CPU 测试理想时钟计划，不用于 runtime；已经移除会假装生效的 fixed microbatch/zero-bubble 参数，并在 API 收到旧的非默认值时拒绝。
- DP worker 错误现在传播到前端，但没有完整启动 deadline、故障重启、socket/pipe超时和动态调度健康协议。
- SHM MQ 是 Python pickle 控制消息共享槽，NCCL 承载 GPU tensor；它不是 shared memory 承载跨 GPU activation。
- 当前 serving runtime 没有可用的量化/混合精度开关，也没有集成 speculative decoding。历史实验的低比特结果很慢且质量不达标，详见[量化与投机解码复盘](量化与投机解码复盘.md)；不能描述成当前功能。
- 端到端同 batch greedy 可复现通过；还缺与 Transformers/HF 的完整 logits/top-k 数值 parity、真实客户端 TTFT、压力下恢复、混合请求和服务 SLO。

## 与官方 vLLM 的对照

对照范围是本机只读 checkout `db9527a46873454610df6dbedf79a36d6bf1a7f6`，不是声称对齐 vLLM 当前最新 main。

vLLM PP 由 model pipeline stage/layer partition、`IntermediateTensors` 与 executor/scheduler 协作，不靠 monkey-patch 模型 forward；本项目已把 PP stage/transport 作为显式模型/worker路径，但仍只有 Qwen 文本路径和简单 step scheduler。vLLM 的 Qwen3 MoE 调用 `FusedMoEFactory`，支持多个 all-to-all backend；DeepEP HT/LL/Nixl/FlashInfer NVLink 等取决于版本、硬件与配置。项目现在是 Torch NCCL `all_to_all_single` variable splits + Python expert GEMM，尚没有融合 dispatch/compute/combine kernel。vLLM multiprocess executor 的 SHM MessageQueue 属于控制面，不是 GPU 张量 collective 的替代品。

官方 Qwen3-Omni thinker 包含 multimodal registry/processor、audio/video parser、vision/audio tower、DeepStack 和 MRoPE 支持；本引擎只有文本 thinker。官方架构可以指导接口边界，不能把一两个类名复制就称支持多模态。
