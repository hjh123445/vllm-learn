# Qwen3-Omni 推理引擎数值正确性排查方法论

本文记录本轮在 172.28.30.56（8×A800 80GB，SM80）上排查 Qwen3-Omni-30B-A3B-Instruct 输出分歧的完整过程。目标不是把某一轮通过率包装成“模型准确率”，而是回答四个问题：

1. 分歧到底发生在哪一个算子、哪一层、哪一个并行边界？
2. 分歧是通信漏数据、权重装载错误、缓存错误，还是低精度执行形状差异？
3. 已经确认并修复了哪些问题，哪些问题仍然没有修好？
4. 以后遇到新的推理结果不一致，如何用一套可复现、可证伪的方法快速定位？

## 一、先把“错误”定义清楚

推理正确性有不同强度，不能把它们混成一个数字：

| 层级 | 比较对象 | 可以回答的问题 | 本轮是否完成 |
|---|---|---|---|
| 组件数值 | 同一输入、权重、算子与参考实现 | RoPE、Linear、Attention、Router、Grouped GEMM 是否实现正确 | 大部分组件已做，仍需扩大形状覆盖 |
| 单步 logits | 同一 token 前缀下的完整词表 logits | 同一个 next-token 计算是否一致 | 匹配执行路径的固定前缀已通过；跨 batch 形状仍有差异 |
| greedy token | 同一前缀下比较 argmax | 是否会改变下一 token | 受 logit margin 影响，不能只看最大绝对误差 |
| 连续生成 | 每一步把上一步输出重新喂回模型 | 端到端输出是否一致 | 单请求受控样本通过，batch 会放大早期分歧 |
| 任务质量 | 公开任务集上的准确率、召回率、ASR 等 | 模型业务效果是否下降 | 本轮没有把未知数据集当作证据，不能宣称任务质量 |

本轮发现的是“数值执行与输出复现问题”，不是重新评估 Qwen3-Omni 的任务能力。`384/384` 的含义是 12 条合成输入、每条 32 个 teacher-forced 位置，不是 384 条独立样本，也不是模型准确率 100%。

## 二、最初是怎样发现问题的

最初观察到：相同模型权重和相同 token 前缀，在 EP1、EP8、PP2×EP4，或者单请求与批请求之间，greedy 输出偶尔不同。这个现象不能直接归因于 EP all-to-all 丢 token，原因有三点：

* 单卡 EP1 也会出现分歧，因此通信不是唯一可能原因。
* 自回归生成一旦第一个 token 不同，后续输入前缀就不同，后面的差异不能再用于定位第一个错误。
* HF 自己的 cached generate、fresh full-prefix forward、不同 Attention backend 也可能产生低精度差异。

因此第一步不是继续跑吞吐，而是冻结输入、权重、软件版本和执行路径，建立可重复的数值诊断环境。每次实验都保存配置、输入 token IDs、源码指纹、环境版本、完整 logits 或选定层张量、输出 token、失败日志和 SHA256 清单。

## 三、完整排查流程

### 1. 固定环境与输入

先记录 GPU 型号、驱动、Torch/Transformers 版本、模型目录、权重文件清单、并行拓扑、dtype、Attention backend、KV cache 配置和 token budget。输入使用本地生成并保存的 token IDs；不读取服务器上来源和许可不明的数据。

对比时必须固定：

* 同一模型权重和 tokenizer；
* 同一 token 前缀、position IDs、attention mask；
* 同一 dtype 和 autocast 设置；
* 同一 prefill/decode 阶段和 KV cache 状态；
* 同一 batch 大小、padding/无 padding 方式和总 M 形状；
* 同一 Attention backend，不能拿 HF cached 结果直接对比自研 fresh 结果。

### 2. 先做 teacher forcing，不先看自由生成

先让 HF 生成一段 continuation，然后把相同的完整前缀逐个输入 HF 和自研引擎，只比较下一 token 的完整 logits。这样每个实现接收的是同一输入，不会把“第一个 token 分歧后输入已经不同”混入定位结果。

每个位置保存以下指标：

* `argmax` 是否相同；
* 最大绝对误差、RMSE；
* top-k 集合交集和分布 total variation；
* HF 第一名与第二名的 logit margin；
* 首个分歧位置和首个分歧层。

若 `2 × max_logit_error < HF top1 margin`，可以把 top-1 稳定性作为一个充分条件；否则只能说数值不同，不能直接说输出错误。greedy 胜者必须用 `torch.argmax`，不能把 `topk(10)[0]` 的第一项当成严格的 argmax，因为并列分数时排序规则可能不同。

### 3. 做 HF 自身对照，排除参考路径问题

本轮发现 HF 单请求与 HF 批量 SDPA 自身也有少量 top-1 差异。原因是 batch 形状可能触发不同的 SDPA kernel 和不同的低精度舍入。因此参考必须分成三类：

1. HF 单请求、fresh full-prefix；
2. HF 批量、与被测实现相同的长度/attention 形状；
3. HF 按请求拆开的 SDPA，对齐自研变长执行方式。

在本轮匹配的执行路径下，自研 EP8 batch 对逐请求 SDPA 参考为 `384/384`，PP2×EP4 batch 对 EP8 batch 也为 `384/384`；这说明该组样本没有发现 EP 结果丢失或 PP/EP 归约漏项。但自研单请求和自研批请求仍有 `373/384` 个 forced-prefix 位置相同，剩余 11 个位置属于跨 batch shape 的数值敏感性。

### 4. 用 EP1 作为隔离基线

先把 EP 设置为 1：

* 如果 EP1 已经分歧，优先查模型数学、权重装载、Attention、RoPE、缓存和 GEMM；
* 如果 EP1 正确、EP8 错误，再查 route 计数、专家归属、all-to-allv、结果回收和归约；
* 如果 EP8 和 PP2×EP4 都一致而 EP1 不一致，不能把问题简单归因于通信。

这一步把“并行错误”和“单卡数学错误”分开，避免一开始就修改 NCCL 代码。

### 5. 组件级 oracle：先验证通信语义，再验证端到端

对变长 EP 通信单独构造可人工计算的输入：每个 source 发送不同长度的 token，覆盖零长度 source、不同 source 长度、不同目标专家、TP2×EP2 和不同 dtype。验证：

* `send_splits`、`recv_splits` 的总和；
* all-to-allv 后 token 的 source ID、原始位置和 expert ID；
* 回收后的排序和 inverse permutation；
* 每个 token 的 top-k route 权重是否保留；
* 专家结果是否按原位置恢复；
* 归约后是否恰好包含所有 route，既不重复也不缺失。

组件 oracle 通过后，才能把端到端差异继续归因给模型算子。它不能替代真实模型验证，但可以排除“通信 API 看起来成功、实际少了 token”的假设。

### 6. 逐层捕获并二分首个差异

捕获范围按模型语义标注，而不是只保存一个黑盒输出：

* embedding；
* 每层 Attention 输入、Q/K/V 投影、输出投影；
* 每层 Router logits、expert IDs、route weights；
* 每层 MoE 输入、专家 grouped GEMM 输出、combine 后输出；
* decoder block 输出；
* final norm 和 lm_head。

捕获工具最初使用 forward hook 读取 module 输入，后来发现 Qwen decoder block 会原地更新 residual，导致 hook 看到的“输入”其实已经被修改。于是改为 `forward_pre_hook` 在模块执行前复制输入，并增加了 `test_activation_capture.py` 回归测试。以后任何逐层诊断都必须先证明 capture 本身没有改变或污染被测数据。

比较时从 embedding 开始，按层向后找第一个不一致的边界。第一个差异出现在哪一层，决定下一步：

* embedding 之前：tokenizer、position、输入拼接或权重；
* Attention 投影：RoPE、Linear、dtype、GEMM shape；
* Attention 输出：Q/K/V、mask、GQA、paged/chunked kernel；
* Router：softmax、top-k、归一化、输入 ownership；
* MoE 输出：专家权重、排序、all-to-allv、grouped GEMM、combine；
* stage 边界：PP send/recv、microbatch 顺序或消息归属；
* lm_head：最终归一化、词表权重或采样。

## 四、已确认的两个实现根因

### 根因一：RoPE 在 CPU 预计算导致设备间舍入不同

旧代码在 CPU 上预先生成完整 sin/cos 表，再把表复制到 GPU。HF 路径是在目标 GPU 上用 FP32 做 inverse frequency 与 position 的乘法、三角函数，然后再按模型 dtype 使用。即使输入公式相同，CPU 与 A800 的三角函数实现和中间舍入也不保证 bitwise 相同。

发现方法：

1. 在 EP1、EP8 中固定同一 Q/K 输入和 position；
2. 单独比较 RoPE 输出，不先看最终 token；
3. 分别运行“CPU 建表后拷贝”和“目标 GPU FP32 建表”；
4. 发现后者与 HF 对齐，而旧路径的微小误差会在 Attention 和后续层传播。

修复方式：`rotary_embedding.py` 在执行设备上用 FP32 生成 position 频率和 sin/cos 表，保持设备迁移时重新建表，最后再转为需要的 dtype。该修复解决的是设备预计算舍入问题，不等于所有低精度 GEMM 差异都被解决。

### 根因二：EP ownership 先切 token 再算 router，改变了 router GEMM 形状

旧 ownership 路径先按 token 所属 source 切出一部分输入，再在这部分输入上计算 router。虽然数学上“每个 token 只算一次”很合理，但 BF16 GEMM 的算法和舍入可能依赖 M 维；把完整输入的 M 改成 ownership 子集后，router logits 可能出现微小变化。Router 后面是离散 top-k，一点小误差就可能改变 expert 选择。

修复方式：

1. 在每个 replicated input 上按完整 M 计算 router logits、top-k 和 route weights；
2. 根据 ownership 只把当前 source 负责的 token/route 分发到对应专家；
3. 使用实际 route counts 的变长 all-to-allv；
4. 目的端只计算本地专家，并按原 token position 返回；
5. source 根据已有 route weight 做 combine；
6. 必要时 all-gather 恢复 replicated 输出。

这样保留了参考路径的 router GEMM 形状，也不会因为先切片而改变离散路由。空 source、变长 source、TP2×EP2 和 source-weight 两种位置的组件 oracle 均通过。该修复减少重复派发的前提是 EP group 内 attention 输入确实是 replicated；不能直接套到每个 rank 输入不同的 attention-DP 布局。

## 五、剩余未解决问题：跨 batch 形状的 BF16 GEMM 敏感性

修完上面两处后，仍然观察到单请求和批请求在相同第一个请求上出现差异。通过 pre-hook 重新取证后，得到两个可复现样本：

| 场景 | 首个差异 | 结果 | 进一步重放 |
|---|---|---|---|
| 47-token，batch=1 vs batch=8 | L0 `q_proj`，101/192,512 元素不同，max abs `1.2207e-4`，RMSE `1.023e-6` | 全 batch 线性一次执行与逐请求 M=47 分段执行不同 | 分段执行结果 exact；单个投影微基准约慢 3.8× |
| 1024-token，batch=1 vs batch=3 | L0 `o_proj`，670,271/2,097,152 元素不同，max abs `0.00390625`，RMSE `3.78e-5` | 第二个 greedy token 从 34859 变为 108704 | 相同输入和权重的 BF16 `F.linear` 重放复现；FP32 输入/权重乘法后转 BF16 在此场景 exact |

短输入 q_proj 的 FP32 累加重放仍有 50 个元素不同，因此“全部改成 FP32 累加”还不是被验证的通用修复。可能影响结果的因素包括 cublasLt 算法选择、M/N/K tile、输入/权重转换、归约顺序、Attention kernel、KV cache 更新和后续 Router margin。

为验证而实现的 `batch_execution_mode=per_request` 会逐请求 forward，固定每次 GEMM 的 M 形状。EP8 的 47-token batch=8、1024-token batch=3，以及 PP2×EP4 的 47-token batch=3，在已测边界上与单请求逐元素一致。但它牺牲批量 GEMM 融合，只能作为回归/保守质量路径，不能称为默认高性能修复，也不能据三个样本证明任意长度、并发和 kernel 都严格确定。

## 六、为什么不能把剩余问题继续叫作“EP 丢结果”

如果 EP 丢 token，通常应在以下证据中看到缺口：route count 总和不守恒、某个 source 的 token ID 消失、专家结果回收数量不符、combine 前后位置缺失，或者匹配执行形状下 EP8 与 EP1 不一致。本轮：

* all-to-allv oracle 覆盖了空 source 和非等长 source；
* EP8 与匹配 Attention 路径的参考对照达到 `384/384`；
* PP2×EP4 与 EP8 的匹配 batch 对照达到 `384/384`；
* 剩余分歧的第一个可见位置出现在 replicated dense Attention projection，而不是 all-to-allv 回收边界。

因此当前证据支持“剩余问题主要是执行形状/低精度路径敏感性”，不支持把所有差异解释成通信漏结果。若未来出现新的 EP 分歧，仍需重新检查 route checksum，不能因为本轮 oracle 通过就永久排除通信错误。

## 七、以后应采用的修复方法论

### 阶段 A：复现与分层

1. 固定源码 SHA、权重 SHA、环境和 GPU；
2. 保存最小输入和完整输出；
3. 先做单请求 teacher forcing；
4. 做 HF 单请求/批量自身对照；
5. 将问题缩小到 EP1、EP8、PP、batch、prefill/decode 中的一个变量；
6. 关闭 profiler、capture、prefix cache 和异步优化，避免诊断工具改变执行图。

### 阶段 B：定位首个可见差异

1. 从 embedding、position、RoPE 开始；
2. 按 Attention、Router、MoE、block、stage 边界捕获；
3. 使用 pre-hook，避免原地 residual 污染；
4. 对张量报告 shape、dtype、finite、max abs、RMSE、非零/NaN 数量；
5. 对路由报告 token ID、expert ID、weight、每专家 count；
6. 对通信报告 send/recv split、source/position checksum 和 permutation；
7. 找到首个差异后，只针对该算子做 replay，不要同时改多个组件。

### 阶段 C：因果验证

每一个“原因”必须满足三件事：

* **可复现**：关闭该因素时差异消失，打开时差异重现；
* **可隔离**：其他输入、权重、路由和形状保持不变；
* **可解释**：修复后的差异位置、方向和规模符合该因素的机制。

例如本轮不是看到 EP 输出不同就猜 NCCL，而是先用 EP1 隔离，再用通信 oracle 排除丢 token，最后在相同输入和权重上复现 BF16 GEMM 的 M 形状差异。

### 阶段 D：修复后的验收门槛

建议至少分四道门：

1. 组件门：FP32 小张量、BF16 真实形状、空/变长输入全部通过；
2. 拓扑门：EP1/EP8、PP×EP、不同 rank 数在匹配执行形状下通过；
3. 执行门：prefill/decode、cached/fresh、batch=1/多请求、短/长上下文分别通过；
4. 业务门：公开且许可明确的数据集上评估任务质量、TTFT、TPOT、吞吐、P95/P99 和显存。

任何一门失败，都要在报告中保留失败日志，不能用另一门的通过结果覆盖。

### 阶段 E：针对当前 batch 问题的后续路线

优先顺序应是：

1. 按 M/N/K 和 dtype 记录实际 cublasLt/CUTLASS 算法，确认是否是算法切换；
2. 对固定 shape 做 FP32 accumulate、FP32 input、BF16 output、确定性 kernel 的逐层消融；
3. 采用 shape bucketing 或固定 tile，把相近请求放进相同 M 形状；
4. 对 Router 记录 top1-top2 margin，低 margin token 触发更高精度重算或稳定 tie-break；
5. 评估 per-request、microbatch 和固定 tile 对 TTFT、TPOT、吞吐、显存的代价；
6. 重新跑长上下文、真实公开任务和连续生成，确认修复不是只对一个合成前缀有效。

不能直接把所有请求串行化作为生产方案：它可以证明“固定 shape 能改善复现”，却会牺牲融合和吞吐。生产修复必须同时满足数值、性能和显存约束。

## 八、多模态到底验证到了什么

### 已加载并验证的内容

本轮使用 HF 的 `Qwen3OmniMoeThinkerForConditionalGeneration`，BF16、SDPA、单卡 GPU2，加载真实预训练视觉/音频 encoder 和 Thinker，输入全部为本地自行生成的媒体，没有读取服务器上的未知数据集：

| 模态 | 输入 | Processor 主要输出 | Thinker forward | 结果 |
|---|---|---|---:|---|
| 图片 | 224×224 白底红色矩形 | `pixel_values=[196,1536]`、`image_grid_thw=[1,3]` | 2.403 s | logits finite |
| 音频 | 1 秒 440 Hz 正弦波 | `input_features=[1,128,100]`、`feature_attention_mask=[1,100]` | 0.297 s | logits finite |
| 视频 | 4 帧合成视频 | `pixel_values_videos=[1152,1536]`、`video_grid_thw=[1,3]` | 9.508 s | logits finite |

原始证据在 `overnight/hf_reference/media_probes.json`、`synthetic_image.png`、`synthetic_audio.npy`、`synthetic_video.npy`。这些是功能 probe，不是模态质量评测，也不代表生产吞吐；时间包括首次 kernel、encoder 和不同媒体形状的影响。

### 当前自研引擎是否只用了 Thinker

是。自研 `model_runner.py` 从 `thinker_config.text_config` 构造 decoder，loader 只映射 `thinker.model.*` 和 `thinker.lm_head`；当前服务入口接收的是文本 `input_ids`，没有 processor、媒体解码、视觉/音频 encoder、媒体 embedding 插入或 Talker 输出路径。

HF probe 也明确只调用 Thinker forward，但在调用前由 HF processor 和真实的视觉/音频 encoder 把媒体转换成 Thinker 所需输入。它证明“官方多模态前端和 Thinker 可以运行”，不证明“自研引擎已经支持多模态 serving”。

`loading_info.json` 中的 `missing_keys` 和 `mismatched_keys` 是空集合；大量 `unexpected_keys` 属于 Talker、code2wav 等未被 Thinker 类加载的权重，这是选择 Thinker-only 类的预期现象，不应误读为 Thinker 权重缺失。Talker 的语音生成、codec、code predictor 和流式音频输出本轮没有加载、没有推理、没有性能数据。

### 为什么多模态不是“把媒体变成 token 就一样了”

媒体不是 tokenizer 直接产生的普通词表 token。完整路径是：

```text
媒体请求
  → 解码/抽帧/重采样/processor
  → 视觉或音频 encoder
  → projection/feature merge
  → 媒体占位符数量与 embedding 对齐
  → 时空位置与 MRoPE
  → Thinker prefill/KV cache/decode
  → （可选）Talker/codec 流式音频输出
```

自研引擎要增加：

* 请求协议中的图片、视频、音频、帧率、时间戳和采样率；
* CPU 解码、抽帧、resize、重采样和媒体预算；
* vision/audio encoder 的权重装载、设备放置和并行；
* encoder feature 与文本占位符的严格数量/顺序对齐；
* 视频时空坐标、音频时间位置和 MRoPE；
* encoder feature cache 与文本 prefix/KV cache 的独立失效规则；
* 混合文本/媒体 batch 的 token budget、显存预算、取消和回收；
* PP stage0 的 encoder 调度，避免每个 stage 重复执行；
* 端到端 trace：上传、解码、encoder、feature handoff、LLM prefill、decode 和输出序列化；
* 若要语音输出，再增加 Talker、codec、code predictor 和流式音频调度。

所以“媒体最终进入 Thinker”只说明 decoder 后半段可以复用，前端表示、位置、缓存、调度和输出链路仍然是新的系统问题。

## 十、面试中的准确表述

可以这样回答：

> 我先用 teacher forcing 和完整 logits 把自回归误差与单步数值误差分开，再用 EP1、变长 all-to-allv oracle 和逐层 pre-hook capture 区分单卡算子、通信和 PP 边界。最终确认并修复了两个实现问题：RoPE 不应在 CPU 预计算后复制到 GPU；EP ownership 不应先切 token 再改变 router GEMM 的 M 维。修复后，匹配执行路径的 EP8 和 PP2×EP4 在限定的合成固定前缀上逐元素对齐。随后发现默认 batch 路径仍受 BF16 GEMM 的 M 形状影响，已实现 per-request 诊断路径，但没有把它包装成生产级全局修复。多模态方面，我验证了 HF 的图片、音频、视频 processor、encoder 和 Thinker 前向；自研引擎目前仍是文本 Thinker，Talker 和多模态 serving 尚未接入。
